# 0004. Lean stack 타당성 — 이미징을 얼마나 직접 구동할 수 있나

- 상태: **inferred**(정적 RE + 에뮬 관측에서의 판정). 전략 문서이며 실기 미검증.
- 전제: "custom OS / 군더더기 최소화" 논의([minimal-sony-footprint] 메모리)에 입력으로 제공. 결론은 "무엇을 재구현할 수 있고, 무엇은 Sony 마법이라 그대로 써야 하는가".

[0001](<0001. liveview-pipeline-overview.md>)~[0003](<0003. sdcom-imaging-control.md>)의 사실을 근거로, **Sony 유저랜드(av-cam.bin + im.elf + libObj) 없이** 최소 프로세스가 라이브뷰를 올릴 수 있는지 평가한다.

---

## 0. 결론 요약

| 질문 | 판정 |
|---|---|
| 라이브뷰를 "표시"만 하는 건? | **가능성 있음(중)** — VPH ch51/스케일러/패널 타이밍은 레지스터로 다 드러나 있다. 하지만 ch51에 넣을 **유효한 YUV 프레임을 만드는 체인**이 문제. |
| ch51에 넣을 영상을 직접 만드는 건(센서→RC)? | **사실상 불가(높은 비용/위험)** — ISP(블랙레벨·디모자이크·WB·감마·결함보정)와 RC 리사이즈가 **문서화되지 않은 하드웨어 + SA DSP 펌웨어**에 묶여 있다. |
| Sony 영상 엔진을 그대로 두고 그 위에 올라타는 건? | **권장** — av-cam이 ch51을 만들게 두고, 우리는 OSD(ch53)만 지배한다. 이것이 이미 검증된 route-b 모델. |

**한 줄**: 영상 생성(센서·ISP·RC·SA DSP)은 **Sony 독점 마법으로 재구현 비현실적**, 재사용 대상. 표시 평면 합성(VPH)·입력·OSD·설정 제어는 **우리가 지배 가능**. 따라서 lean stack = "Sony 이미징 코어 유지 + Sony UI/Android 군더더기 제거"가 현실적 상한선.

## 1. 재사용 불가(Sony 독점 마법) — 반드시 그대로 써야 하는 것

### 1.1 센서 결함보정 / SA DSP (`ZIT ConvZ1C`)
- 이미저 start는 **SA DSP 코어0(0xF34A0000)** 에서 센서 결함 테이블을 변환(`ZIT ConvZ1C 43990B2C`)해야 진행된다(RE_SA_DSP §0, RE_LIVEVIEW_REQUEST §0). SA 코어에는 별도 DSP 펌웨어(`sabin`, ODL로 DRAM 로드)가 올라가며, 완료는 IRQ 51 + 메일박스 응답으로만 온다.
- 이 변환/프로그램(program id 2)과 그 입력 결함 테이블은 **공장 캘리브 데이터**에 묶여 있고 알고리즘은 미공개. 재구현 = 사실상 불가.

### 1.2 ISP 파이프라인 (CamCore develop/YC)
- RAW→YC 변환(블랙레벨, 디모자이크, 화이트밸런스, 감마, 노이즈리덕션)은 **CamCore 블록 내부**에서 일어나고(LIVEVIEW_IMAGE §2.3), 별도 develop DMA가 영상 데이터를 나르지 않는다. 튜닝 파라미터/계수는 Sony 전용.
- 재현하려면 전체 ISP 수학 + 센서별 튜닝이 필요 → LIVEVIEW_IMAGE §4.1의 B3(sensor RAW 주입)이 "very large"로 평가된 이유.

### 1.3 RC 리사이즈 엔진 (0xF3880000)
- 1728→1024 폴리페이즈 H 리사이즈, 포맷 코드 0xA, 크롭 워드가 미디코드(LIVEVIEW_IMAGE §4.1 b2). 입력(IIB)에서 ch51 포맷으로 바꾸는 유일 지점.

### 1.4 센서 레지스터 시퀀스
- P2S는 쓰기 전용, 센서 ID read-back 없음([0002 §1]). 노출/게인/리드아웃 테이블(`dw_43BDD108` 등)이 미디코드. 센서를 "직접" 돌리려면 이 테이블 전부를 역설계해야 함.

### 1.5 공장 캘리브 / 부팅 의존
- 캡처는 dmm 메모리 레이아웃 + Backup 부트팩터(0x51000F)에 의존(RE_STILL_CAPTURE §0). 이미징 코어는 공장 데이터·부팅 상태와 깊게 얽혀 있어, Sony 부팅/엔진 초기화를 통째로 들어내는 건 벽돌·동작불능 위험이 크다.

## 2. 재사용 가능(우리가 지배 가능) — lean stack에서 우리 코드로 대체 가능한 것

| 영역 | 레지스터/인터페이스 | 상태 |
|---|---|---|
| **VPH 표시 평면 합성** | 0xF3440000~0xF3446FFF, ch51(YUV)/ch53(OSD), 스케일러 0x300, 패널 타이밍 0x5000 | 레지스터·비트필드 전수 매핑됨(vdf_vph_regs.txt). display/0003 |
| **OSD 평면(ch53)** | `+0x20` start-addr 단일 레지스터가 패널 OSD 소스 | 우리가 간접 지배(detour-swap), route-b 검증됨 |
| **입력** | evdev `/dev/input/event0` + ABT | input 카테고리, 키맵 확정 |
| **설정 제어면** | SDCom 0x1540432(노출/AF/캡처), Backup 화이트리스트 | sdcom/backup 카테고리, Get/Shift 실기 성공 |
| **타이밍 이해** | SYSV V = 엔진 프레임(33367µs), 패널 vsync 60Hz 디커플 | [0001 §3], 에뮬로 실증 |

- VPH는 Linux가 전혀 건드리지 않는다(DISPLAY_SCANOUT §0: im.elf/libObj/gralloc에 0xF344xxxx 접근 0건). 즉 **표시 평면은 av-cam 소관**이고, 우리 프로세스가 그 평면을 지배하려면 VDF가 `+0x20`에 쓰는 phys를 바꾸는 식(route-b)이거나 VDF 자체를 대체해야 한다.

## 3. "최소 프로세스로 라이브뷰" 시나리오별 평가

| 시나리오 | 필요한 것 | 판정 |
|---|---|---|
| **A. av-cam 유지 + 우리 OSD** | OSD 레코드를 VDF에 보내거나(ch53) detour-swap | **현실적·검증됨**(route-b). 영상=Sony, UI=우리. **권장 lean stack** |
| **B. av-cam 없이 ch51에 Sony 엔진이 만든 프레임 재사용** | av-cam을 떼면 ch51 producer가 사라짐 | 모순 — A로 귀결 |
| **C. av-cam 없이 우리가 ch51 프레임 생성** | 센서 P2S 시퀀스 + SA DSP 펌웨어 + ISP + RC 전부 재구현 | **비현실적**(§1 전부). 센서 테이블·ISP 튜닝·SA 바이너리 미공개 |
| **D. 테스트/고정 영상만 표시** | VPH ch51에 우리 YUV 버퍼 프로그램(스케일러·타이밍은 레지스터로) | **기술적으로 가능**하나 VPH 태스크를 띄우고 vsync(101/102) 서비스해야 함. 실영상 아님(디버그/특수용) |

## 4. Lean stack 설계 함의 (custom OS 논의 입력)

1. **이미징 코어(av-cam + SA DSP + 센서/ISP/RC)는 블랙박스로 보존한다.** 이것이 Sony의 "영상·엔진 SW 처리"이며([minimal-sony-footprint]) 재구현 대상이 아니다. 들어내려는 "군더더기"는 그 위의 **Sony UI 레이어(viewUnified*.so 메뉴/OSD)와 Android 스택**이지 이미징 코어가 아니다.
2. **우리가 소유할 경계는 표시/입력/제어면**: VPH OSD 평면(ch53), evdev+ABT 입력, SDCom 제어, Backup 설정. 이 경계는 전부 레지스터/인터페이스가 드러나 있고 벽돌 위험이 낮다.
3. **영상 평면(ch51)은 "읽기전용 관전자"로 취급**: 우리는 그 위에 OSD를 합성할 뿐, 프레임을 만들거나 가로채지 않는다. 라이브뷰를 끄고 패널 전체를 Android 평면으로 가져가는 ABT 월드 스위치는 RAM-only로 못 켜므로(display/0003 §2) 공존 모델(OSD만)이 유일하게 안전.
4. **부팅/초기화 의존 주의**: 이미징 코어는 공장 Backup·부트팩터·dmm 레이아웃에 얽혀 있어(RE_STILL_CAPTURE), av-cam 부팅 경로를 임의로 바꾸면 라이브뷰/캡처가 조용히 죽는다. lean stack은 **av-cam 부팅을 건드리지 않는** 범위에서만.

## 5. 재검증이 필요한 지점(결론을 뒤집을 수 있는 것)

- 라이브뷰가 **루마 전용**(param[24]=1)이 실제인지. 실기는 컬러이므로 C-plane 경로가 다른 모드 상태에서 열린다면, ch51 producer 재사용 모델(A)에는 영향 없지만 D(직접 생성)의 포맷 요구가 바뀐다(LIVEVIEW_IMAGE §3).
- VDF를 우리 프로세스로 **부분 대체**해 ch51 producer를 유지하면서 OSD/합성만 우리가 하는 중간안의 비용(현재 route-b는 detour-swap으로 우회).
- 모니터링 상태 전이를 유발하는 SDCom 요청을 standalone에서 보낼 수 있는지([0003 §6]).
