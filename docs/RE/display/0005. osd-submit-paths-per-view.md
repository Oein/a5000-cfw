# 0005. 뷰/모드별 ch53 OSD 제출 경로 — funcMode 23에서 우리 메뉴가 안 뜨는 근본 원인

- 상태: 정적 RE 확정(libObj.so 1.10, `sub_XXXX` 교차확인). 레코드 레이아웃 분기 = PROVEN, FbContainer 레코드의 phys 해석 일부 = [?](device-seal).
- 대상: `im.elf` / `libObj.so` 1.10. 디컴파일 출처 `packages/data/re/ida/libObj.so.c`(로컬 전용).
- 관련: 0002(present 파이프라인), 0003(패널 라우팅), 0004(Rigel 클라), camera/0001(funcMode enum).

## 0. 결론 (TL;DR)

1. **촬영(SHOOTING)과 메뉴/정보/재생(MENU·DISP·PLAY)은 ch53로 가는 제출 경로가 다르다.** 둘 다 최종적으로 `vdf_if_port_send_update`(`sub_5DC3D4`)를 통과하지만, **32B OSD 레코드의 레이아웃이 서로 다르다.**
   - 촬영: **SenserIf**(`sub_5D99D0`)가 grm_sens_work 전체화면 평면을 **직접** 제출 — phys가 레코드 **`+20`**, 상수 `0x103`가 **`+16`**.
   - 메뉴/정보/재생: **UpdateManager/FbContainer 위젯 경로**(`sub_5DD33C`→`sub_5DCC1C`→`sub_5DC3D4`)가 **그 뷰 자신의 per-element 프레임버퍼**를 제출 — `gen_struct_for_update`(`sub_5DD190`) 레코드는 BMP 핸들을 **`+28`**, 컨테이너 필드를 **`+16`**에 두고 **`+20`에 raw phys를 쓰지 않는다.**
2. **그래서 우리 detour-swap은 촬영에서만 이긴다.** `my_vdfSend`는 (a) 지오메트리가 640/480인 레코드만 "패널"로 보고 (b) phys를 **`+20`에만** 덮어쓴다. 이는 **SenserIf 촬영 레코드 전용**이다. funcMode 23의 FbContainer 레코드는 phys가 `+20`에 없으므로 우리 swap이 아무 효과가 없고, **순정 메뉴/정보 뷰의 FB가 계속 ch53를 소유**한다 → 우리 UI가 버퍼에 그려져도 패널에 안 뜬다. ★근본 원인.
3. **funcMode 23 진입 트리거 = DISP(및 MENU edge 누수).** stock-shooting passthrough에서 우리 입력훅은 **MENU(0x11)만** peek/consume한다(`input_createevent.cpp:145`). **DISP는 소비하지 않아** 순정으로 흘러가 `ViewShootingInfoDisp`(전체정보 DISP = funcMode 23)를 띄운다. 일단 23에 들어가면 위젯 경로가 ch53를 잡고, 우리가 MENU를 소비해도 순정은 23에서 안 빠져나와 고착된다.
4. **수정 방향(우선순위):** ① 순정을 **촬영 funcMode에 묶어** 두기 — passthrough에서 DISP도 소비해 23 진입을 차단(그러면 ch53 구동자는 SenserIf 하나뿐 → 기존 swap이 그대로 이김). ② 보강으로 **우리 메뉴가 떠 있는 동안 UpdateManager present를 비활성**(`mgr+100`=UPDATEMGR_PRESENT_DISABLE_WORD=1)해 위젯 경로가 ch53를 다시 못 잡게 한다. ③ 최후책: `my_vdfSend`가 FbContainer 레코드 포맷도 인식해 swap(취약, 비권장).

## 1. ch53 OSD 평면을 프로그램하는 모든 경로

패널 OSD 소스 = VPH ch53 `+0x20` 단일 레지스터(0003). 그 레지스터를 궁극적으로 쓰는 것은 VDF 워커 스레드이고, 워커에 레코드를 post하는 함수는 **오직** `vdf_if_port_send_update`(`sub_5DC3D4` @0x5DC3D4; type 5 메시지, osal 큐 0x7FFFBB)다(0002 §1). 그 함수를 호출하는 상위 경로는 두 갈래다.

| # | 상위 경로 | 함수 | 레코드를 만드는 곳 | 비고 |
|---|---|---|---|---|
| A | **SenserIf 엔진 OSD** | `sub_5D99D0` → `sub_5DC3D4` **직접** | 스택 `v13..v21`, grm_sens_work 전체화면 | UpdateManager 우회 |
| B | **UpdateManager 위젯 커밋** | `sub_5DD33C`/`sub_5DD2E4` → `sub_5DCC1C` → (변경게이트 통과 시) `sub_5DC3D4` | `FbContainer::gen_struct_for_update`(`sub_5DD190`) | 변경게이트 `sub_5DCAB4`, 캐시 `mgr[43..]` |

`sub_6789E8`(Rigel GL 합성)은 Android/메인서피스 평면으로만 가고 ch53에 안 닿는다(0003 §2, 0004). 따라서 ch53 경쟁은 A vs B 둘뿐이다.

### 1.1 경로 A 레코드 (SenserIf, `sub_5D99D0`) — PROVEN

```
dest = BMP_CreateFromPhys(640,480, fmt=2, 0, dword_EEED1C, 640, &dest, &v23, ...)
+0  dest (BMP RectangleRecord, 640x480 지오메트리 내장)
+4  HIWORD(dest)   +6 WORD2(dest)   +10 ...
+12 bpp (BMP_PixelFormatToBytesPerPixel)
+16 = 259 (0x103)        ← 상수(핀/레이어 id)
+20 = dword_EEED1C       ← ★ raw phys (grm_sens_work 전체화면 평면)
+24 = 4
+28 = v23 (BMP obj)
→ sub_5DC3D4(&v13, 1)   // 한 장짜리 전체화면 레코드
```

우리 instrument 로그의 실측 레코드 `{0, 480,640, 480,640, bpp=2, flags, PHYS@+20, 2, bmp}`와 일치. `isPanel`(640/480) 참, phys `+20` → **우리 swap이 정확히 맞는다.**

### 1.2 경로 B 레코드 (FbContainer, `sub_5DD190` = `gen_struct_for_update`) — PROVEN

`sub_5DD33C`가 컨테이너 2개(`a1+88`, `a1+200`)의 dirty element를 모아 각 element마다 `gen_struct_for_update`로 32B 레코드를 만든다(최대 2개). 레이아웃:

`gen_struct_for_update`는 먼저 element FB에서 BMP 핸들과 픽셀포맷을 조회(`sub_5DCE82`)한 뒤 32B 레코드를 채운다. 32B 레이아웃(오프셋 맵):

```
+0..+10  BMP rect 지오메트리 (조회한 BMP의 좌표/크기)
+12      bpp (BMP 픽셀포맷에서 산출)
+16      컨테이너 필드(핀/레이어 id 계열; 경로 A의 +16=0x103과 같은 자리)
+20      (쓰지 않음)   ← ★ raw phys가 여기에 없다
+24      픽셀포맷 코드
+28      element FB의 BMP 핸들   ← ★ VDF가 이걸로 FB/phys를 해석
→ sub_5DCC1C(제출) → (게이트) → sub_5DC3D4(mgr+43, count)
```

**경로 A와의 결정적 차이:** 경로 A는 phys를 레코드에 **raw(`+20`)로 박아** 넣는다. 경로 B는 phys를 **BMP 핸들(`+28`)로만** 전달하고 `+20`은 안 쓴다(그리고 지오메트리는 element FB의 rect — 전체화면 메뉴 FB면 640/480일 수 있으나, 중요한 건 phys 전달 방식이다). VDF 워커는 경로 B 레코드에서 **`+28`의 BMP 핸들로 순정 메뉴 FB의 phys를 얻어** ch53 `+0x20`에 쓴다. 우리가 `+20`을 덮어도 그 값은 경로 B에선 참조되지 않는다.

> [?] device-seal: VDF 워커(message type 5 핸들러)가 경로 B 레코드에서 phys를 `+28`(BMP 핸들) 경유로 푸는지, `+16`을 phys로 재해석하는지의 **정확한 필드**는 정적으로 못 박았다(두 빌더의 저장 순서로 레이아웃 분기는 확정). 실기/에뮬에서 funcMode 23일 때 hook instrument 로그로 레코드 덤프를 뜨면 즉시 확정된다.

### 1.3 변경게이트 `sub_5DCAB4` (경로 B 전용) — PROVEN

`sub_5DCC1C`는 `sub_5DCAB4`가 1을 줄 때만 `sub_5DC3D4`를 부른다. 게이트는 `a1[25]`(=`mgr+100`, PRESENT_DISABLE)==1이면 **무조건 0(제출 안 함)**, `a1[24]`(=`mgr+96`, 강제-1회)==1이면 1, 레코드 개수/키필드(`+26` 상당) 변화 시 1. **경로 A(SenserIf)는 이 게이트를 통과하지 않는다**(직접 호출). ⇒ 뒤 §3의 수정책 ②가 성립하는 근거: `mgr+100=1`은 경로 B만 끄고 경로 A는 안 끈다.

## 2. 뷰/모드별 제출 경로 매핑 + 우리 hook 커버 여부

| 뷰 / funcMode | ch53 제출 경로 | 레코드 포맷 | 우리 detour-swap이 먹히나? |
|---|---|---|---|
| 촬영 P/A/S/M (3~6), iAuto/SCN (7/8), 폴백(1) | **A: SenserIf** `sub_5D99D0` | phys@+20, 지오 640/480 | **예.** `isPanel` 참 + phys@+20 일치 → ch53가 우리 버퍼 latch |
| **MENU (23, `ViewSettingMenu`)** | **B: FbContainer** `sub_5DD33C`→`sub_5DCC1C` | BMP핸들@+28, phys@+20 없음 | **아니오.** `+20` 덮어도 무효, 순정 메뉴 FB가 ch53 소유 |
| **DISP 전체정보 (23, `ViewShootingInfoDisp`)** | **B: FbContainer** (+ 배경 라이브뷰는 ch51 별도) | B 포맷 | **아니오.** 동일 |
| **재생 (21, `ViewSinglePb`)** | **B: FbContainer** 위젯 경로 | B 포맷 | **아니오.** 동일 |

(촬영에서도 위젯 element가 dirty면 경로 B 레코드가 간헐 제출될 수 있으나, 패널 전체를 차지하는 OSD는 SenserIf 전체화면 레코드다. 그래서 촬영에선 우리 swap이 ch53를 쥔다 — 실기 관측과 일치.)

## 3. 근본 원인 (funcMode 23에서 우리 메뉴가 안 뜨는 이유) + 근거

1. **(진입)** passthrough에서 DISP는 우리가 안 먹으므로 순정으로 가서 `ViewShootingInfoDisp`(23)를 띄운다. (MENU도 edge/타이밍에 따라 순정 메뉴를 열면 `ViewSettingMenu`=23.) → 순정이 funcMode 23. 핸들: `getCurrentFuncEventMode`@0x394924, 뷰스택 `dword_EEDDD8`, 현재뷰 `dword_EEDDE0`.
2. **(소유권)** 23에서 ch53는 **경로 B(FbContainer 위젯)**가 그 뷰의 FB로 구동한다(§1.2, §2). `sub_5DCAB4`를 통과한 매 커밋마다 순정 FB가 ch53 `+0x20`에 (재)latch된다.
3. **(hook 미스매치)** 우리 `my_vdfSend`는 **경로 A 레코드 가정**으로만 동작한다 — `isPanel`(640/480) 그리고 phys를 **`+20`에만** 기록. 경로 B 레코드는 phys가 `+20`에 없고 `+28`(BMP 핸들)로 전달되므로 **우리 swap이 no-op** → 순정 메뉴/정보 FB가 ch53를 계속 소유. 우리 worker가 우리 버퍼에 메뉴를 렌더해도 ch53는 그 버퍼를 가리키지 않는다 → **패널 미표시.**
4. **(고착)** 우리가 MENU를 소비하므로 순정이 23에서 못 빠져나온다. single-buffer in-place(0002)는 "ch53가 이미 우리 phys를 latch한 상태"를 전제로 하는데, 23에선 그 전제가 깨진다(latch가 순정 FB).

이는 "별도 제출 경로가 우리 hook을 우회한다"는 가설을 **부분 정정하며 확정**한다: 우회하는 게 아니라 **같은 `sub_5DC3D4`를 통과하되 레코드 포맷이 달라** 우리 swap 조건에 안 걸린다.

## 4. 수정 방향 (벽돌 0 · RAM-only · 가역)

### ① (1순위) 순정을 촬영 funcMode에 묶기 — 23 진입 차단
- `input_createevent.cpp`의 passthrough peek에 **DISP도 추가**(촬영 중 순정 정보뷰 토글을 소비). 우리 overlay 활성 시 DISP는 우리 `shooting_osd`의 `infoOn_` 토글(이미 구현)로만 쓰고 순정엔 안 넘긴다.
- MENU 소비가 순정 메뉴 open을 **확실히** 막는지 edge(press/release) 기준 재점검. 순정이 이미 23이면 우리 메뉴 open 전에 **순정을 촬영으로 되돌려야** 한다(아래 ②로 보강 또는 복귀 키 주입).
- 효과: ch53 구동자가 **SenserIf(경로 A) 하나뿐** → 기존 swap이 그대로 이김. 우리 커스텀 메뉴는 "촬영 OSD 평면 위에 얹는 오버레이"로 동작([[route-b-stock-osd-passthrough]] 설계와 일치).

### ② (보강) 우리 메뉴 동안 UpdateManager present 비활성
- 우리 메뉴 스크린이 push되는 동안 `mgr+100`(`UPDATEMGR_PRESENT_DISABLE_WORD`, 이미 engine.h/Path A에 plumbed)을 **1**로 세운다 → `sub_5DCAB4`가 `a1[25]==1`로 **경로 B를 early-out**(제출 안 함) → 순정 위젯 FB가 ch53를 다시 못 잡는다. pop 시 원복.
- 경로 A(SenserIf)는 게이트 밖이라 영향 없음(§1.3) → SenserIf가 계속 제출 → 우리 swap으로 우리 버퍼가 ch53에 latch 유지. **①과 함께 쓰면 23 고착 상황에서도 우리 OSD가 이긴다.**
- 주의: `mgr+96` 강제-submit은 에뮬에서 stock walk 희소로 무효였음(0002 §3) → present 레이트용으로 쓰지 말 것. 여기선 `mgr+100`(끄기)만 사용.

### ③ (최후책, 비권장) FbContainer 레코드도 swap
- `my_vdfSend`가 경로 B 레코드(BMP핸들@+28, phys 비-+20)를 인식해 우리 FB로 바꾸기. 두 포맷이 경쟁하고 정확한 phys 필드가 device-seal(§1.2 [?])이라 취약. ①+②로 23를 안 만들면 불필요.

### 또는: 순정 23를 아예 피하는 구조
[[route-b-stock-osd-passthrough]] 방침대로 **우리 UI는 촬영 funcMode 위 오버레이로만** 존재하고, 순정 MENU/DISP 전체뷰는 **진입 자체를 봉쇄**(①)하는 것이 가장 견고하다. 순정 23 뷰를 "우리 것으로 덮기"보다 "안 열리게 하기"가 정답.
