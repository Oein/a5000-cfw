# 0001. GPU 합성 조사 — 라이브뷰 중 OSD를 GPU로 패널에 합성할 수 있는가

- 상태: 종결 (에뮬레이터 + 정적 RE, 2026-11)
- 대상: Sony a5000 (ILCE-5000) 펌웨어 1.10, `im.elf` / `libObj.so`
- 판정: **불가능.** 단, 성능 한계의 진짜 원인은 GPU 부재가 아니라 CPU 쓰기 매핑이 uncached라는 점이며, 이는 GPU 없이 고칠 수 있다.

> ⚠️ **2026-11-20 정정 (0007):** 본문의 "순정 OSD는 GPU 없이 CPU가 래스터화"는 **틀렸다** — 순정 UX는 촬영 화면까지 GLES2로 그린 뒤 eglSwap→PPF로 linear 패널 버퍼에 옮긴다. 다만 "GPU 합성으로 갈아탈 실익 없음(바닥=매핑)"이라는 **결론 자체는 0007 §5에서 유효함이 재확인**됐다. GPU로 ch53을 만드는 것은 가능하나 Recipe A(0006) 대비 실익 ≈ 0.

## 1. 질문

라이브뷰(촬영 대기) 중에 우리 커스텀 OSD를 GPU로 그려 패널에 합성할 수 있는가. 가능하면 CPU 블릿 비용을 없앨 수 있다.

## 2. 불가능한 이유 (3가지)

### 2.1 순정 촬영 OSD는 GPU가 아니라 CPU가 래스터화한다

- `GRM_bitmapWriteLockBits` (libObj `0x555B4C`)는 GRM 비트맵의 **CPU 쓰기 포인터**를 반환한다. 위젯은 이 포인터에 직접 픽셀을 쓴다.
- `GRM_bitmapCreateComposite` (libObj `0x555A44`)는 스텁이며 `-9999`를 그대로 반환한다. 즉 "여러 비트맵을 GPU로 합성"하는 공개 경로가 실제로는 동작하지 않는다.
- libObj에는 GPU draw/blit API가 없다. 순정 OSD 파이프라인에는 GPU가 끼어 있지 않다. (0002 참조)

### 2.2 유일한 GPU 합성기는 패널에 닿지 않는 평면으로 출력한다

- GPU 합성기는 Rigel WindowServer의 합성 함수 `sub_6789E8` (`0x6789E8`)이다. 동작은 `ws_hal_lock` 후 `glGenTextures`, `glTexImage2D(GL_RGBA)`로 텍스처를 올려 GL 합성하는 것이다.
- 이 출력은 **Android/메인서피스 평면**으로 간다. 라이브뷰 중에는 이 평면이 패널(ch53)에 노출되지 않는다.
- 레지스터 레벨로 증명했다. RGLTEST(별도 프로세스 Rigel 클라이언트, 0004)를 돌리는 동안 VPH ch53 start-addr는 순정 엔진 버퍼 `0x8f7ee000` / `0x8f758000`만 오갔고 우리 버퍼로는 한 번도 바뀌지 않았다.

### 2.3 패널 OSD 소스는 단일 레지스터이며 평면 mux가 없다

- 패널 OSD 소스를 정하는 것은 VPH 레지스터 `+0x20` (PA `0xF3441320`) 하나다. 그 값이 가리키는 물리 버퍼가 곧 패널 OSD다.
- "엔진 OSD"와 "Android/Rigel 평면" 사이를 고르는 mux는 존재하지 않는다. (0003 참조)

## 3. 실제 발견 — 성능 한계는 GPU 부재가 아니다

초기에는 "GPU를 못 쓰니 CPU 블릿이 느린 것"으로 이해했다. 실제 병목은 **매핑 속성**이다.

| 항목 | 우리 (`VdfDisplay`) | Sony 순정 |
|---|---|---|
| 매핑 장치 | `/dev/mem` | `/dev/stream` (liro.ko) |
| 캐시 속성 | **UNCACHED** | **CACHED** |
| 쓰기 처리량 | 약 8 MB/s (CPU 쓰기) | 캐시 write-back 후 DMA 전에 dcache clean |
| 근거 | `packages/custom-binary-app/platform/a5000-inproc/display_rigel.cpp:709` (`/dev/mem` open + mmap) | MA 매퍼 `sub_5E7860` (`0x5E7860`) |

- `sub_5E7860`은 SDRAM 물리주소(device=null)에 대해 `/dev/stream`을 선택한다. 순정은 같은 물리 버퍼를 캐시 가능 매핑으로 쓰고, DMA 스캔아웃 전에 명시적으로 dcache clean을 한다 (liro/upm 캐시 연산).
- 우리 쪽은 같은 물리 버퍼를 `/dev/mem` uncached로 매핑하기 때문에 픽셀 한 개 쓰기마다 버스 트랜잭션이 발생한다.

## 4. 결론 및 수정 방향

- GPU 합성은 포기한다. 얻을 이점이 없고 패널에도 닿지 않는다.
- 수정 방향은 **cached 매핑 + dirty-span 단위 dcache clean**이다. GPU가 필요 없고, 쓰기 처리량이 약 8 MB/s에서 수백 MB/s 수준으로 오를 것으로 기대한다.
- 상태: 진행 중 (실측 전). 이 변경은 RAM 매핑만 바꾸므로 플래시 접촉이 없고 가역이다.
