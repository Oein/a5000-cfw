# 0002. present 파이프라인 — OSD에서 ch53까지, 그리고 route-b present

- 상태: 순정 경로 식별 완료, route-b 반응성 해결 (에뮬 2026-11-19), 남은 한계는 uncached 매핑(0001)
- 대상: `im.elf` / `libObj.so` 1.10

## 1. 순정 경로

GPU는 관여하지 않는다.

1. 위젯이 GRM BMP를 CPU로 래스터화한다 (`GRM_bitmapWriteLockBits` `0x555B4C`가 CPU 쓰기 포인터를 줌).
2. `sub_5D99D0` (`0x5D99D0`, SenserIf)가 `BMP_CreateFromPhys`로 32바이트 레코드를 만든다. 물리주소는 레코드 `+20`.
3. `vdf_if_port_send_update` (`sub_5DC3D4`, `0x5DC3D4`)로 VDF에 제출한다.
4. VDF 워커가 VPH ch53의 `+0x20` start-addr를 프로그램하고 DMA 스캔아웃이 일어난다.

레코드(32B) 실측 레이아웃: `+12`=bpp(16), `+16`=flags, `+20`=phys, `+24`=2, `+28`=bmp(서피스 id). 포맷은 640x480 16bpp RGBA4444이고 알파=0인 부분은 라이브뷰가 투과된다.

변경 게이트 `sub_5DCAB4`: `mgr+100`(PRESENT_DISABLE)이 1이면 건너뛰고, `mgr+96`(FORCE_SUBMIT)이 1이면 `+28` 비교 전에 제출을 강제한다. 단 1단계에서 `count==0`이면 건너뛰므로 dirty element가 필요하다. dirty 마킹(`sub_5DCD80`)은 컨테이너 뮤텍스 아래 `std::vector::push_back`이라 lock-free로 건드릴 수 없다. 자유구동 vsync 루프는 libObj 내부에 없고, present walk `sub_5DD33C`는 im.elf의 GLES swap commit(`sub_644C80` / `sub_5342B4`)이 구동한다.

## 2. route-b 1단계: detour-and-swap

- 우리 워커 스레드에서 `vdf_if_port_send_update`를 직접 호출하면 im.elf가 크래시(워치독)한다. VDF OSD 제출은 stock SenserIf 스레드와 연결된 OSD pin `0x59000E` 컨텍스트를 요구하기 때문이다.
- 해법: `vdf_if_port_send_update`를 후킹(LDR.W PC 패치, unpatch-call-repatch 방식 call-through, spinlock 직렬화)하고, **stock 제출 스레드 안에서** 패널 OSD 레코드의 `+20` phys를 우리 버퍼로 치환한다. 제출 자체는 stock이 수행하므로 컨텍스트 조건이 충족되어 크래시가 없다.
- 우리 버퍼는 `utilGetMemory` (`sub_5D9AEC`, `0x5D9AEC`)로 확보한다 (MA_CreateSpace "grm_sens_work" type 268054 후 Alloc, LogicalToPhysical). 에뮬에서 phys는 `0x9ac00000`이었다.
- 에뮬 검증: 라이브뷰 ON에서 route-b OSD가 라이브뷰 위에 HW 합성되고 im.elf 80초 이상 무크래시.

## 3. route-b 2단계: single-buffer in-place (커밋 e303d93)

- 증상: 메뉴 반응이 나빴다. 에뮬 baseline에서 패널 제출이 약 1회/초였다.
- 원인: double-buffer는 새 back 버퍼가 **다음 stock 제출 때까지 latch되지 않는다.** 제출 캐던스(약 1/s)에 묶인 것이 랙의 원인이었다. 우리 hook은 `+20`만 바꾸는데 게이트는 `+28`을 비교하므로 hook만으로 게이트가 열리지도 않는다.
- 결정적 관찰: 소프트웨어 OSD 백엔드는 제출 0회로 scanout 버퍼를 직접 써서 full-rate로 동작했다. 즉 **ch53 OSD 스캔아웃은 매 프레임 버퍼를 다시 읽는 연속 스캔아웃**이다.
- 해법: 버퍼 하나를 첫 stock 제출 때 latch(single이라 매번 같은 phys)하고, `present()`가 매 프레임 그 버퍼를 제자리에서 렌더한다. 쓰기가 즉시 보이므로 제출 캐던스와 분리된다.
- 반증: `mgr+96=1`을 30 Hz로 써도 제출률은 1/s 그대로였다(stock walk 자체가 희소). force-submit 경로는 에뮬에서 무효.
- 실측(에뮬, 키 입력부터 첫 가시 변화): single-buffer 약 0.18 s, 순정 Sony 메뉴 약 0.28 s, 구 double-buffer 약 0.45 s(0.12~0.54 변동). 순정급 이상의 반응성.

## 4. route-b 3단계: 행(row) 단위 dirty 추적

- 메뉴/모달에서 남은 끊김은 매 프레임 고정 약 20 ms의 **전체 프레임 memcmp**였다.
- 수정: Canvas가 그려진 열 범위(column span)를 행별로 기록하고, present는 그려진 행만 스캔해 변경분만 기록한다.

## 5. 남은 한계

단일 버퍼를 `/dev/mem`(uncached)으로 쓰는 쓰기 비용이 바닥이다. cached 매핑 + dirty-span dcache clean으로 해결하는 작업이 진행 중이다 (0001 3~4절). 실기 검증은 별도.
