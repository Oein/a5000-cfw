# 0003. 패널 라우팅 — VPH가 무엇을 합성하는가

- 상태: 확정 (에뮬 디스플레이 모델 + 레지스터 관측, 2026-11-19)

## 1. 구조

패널(console0)은 VPH(cxd90014)가 **두 평면**을 HW 합성한 결과다.

| 평면 | 내용 | 포맷 |
|---|---|---|
| AIF ch51 | 비디오(라이브뷰) | YUV |
| AIF ch53 | OSD | 16bpp RGBA4444 |

- ch53의 소스는 **단일 레지스터 `+0x20` start-addr** (PA `0xF3441320`)다. 여기에 적힌 물리주소의 버퍼가 곧 패널 OSD다.
- "엔진 OSD"와 "Android/Rigel 평면" 중에서 고르는 mux는 **없다.**
- 근거: 에뮬레이터 모델 `emulator/qemu-overlay/hw/display/cxd90014_vph.c`의 `vph_update()`가 ch51 + ch53 두 평면만 합성하고 다른 소스를 갖지 않는다.

## 2. GPU(Rigel) 출력의 위치

Rigel WindowServer의 GL 합성(`sub_6789E8`, `0x6789E8`)은 Android/메인서피스 평면으로 출력되며 ch51/ch53 어느 쪽에도 연결되지 않는다. 라이브뷰 중 ch53은 순정 엔진(UpdateManager/SenserIf, 이후 `vdf_if_port_send_update` `0x5DC3D4`, 이후 VDF)이 독점하고 `+0x20`을 프로그램한다.

Android 평면이 패널 소스가 되는 유일한 경로는 엔진의 Android-foreground 모드 전환인데, 이는 ch51(라이브뷰)을 끄고 패널 전체를 가져가므로 라이브뷰와 공존할 수 없다. 트리거는 ABT 월드 스위치이며 클라이언트가 RAM-only로 켤 수 없다 (device-seal).

## 3. 귀결

- detour-swap(0002)이 패널에 닿는 이유: stock VDF가 `+0x20`에 쓰는 phys를 레코드 단계에서 우리 버퍼로 바꿨기 때문이다. 같은 레지스터 하나를 우리가 간접 지배한다.
- 별도 프로세스 Rigel 클라이언트가 못 닿는 이유(0004): 그 출력은 `+0x20`에 영향을 주지 못한다.
- 관측: 라이브뷰 ON, RGLTEST 실행 내내 ch53 start는 `0x8f7ee000`와 `0x8f758000`만 토글했다.

## 4. 한계

에뮬 모델 기반 결론이다. 레지스터 맵 자체는 실기 SoC와 일치하도록 만들었으나, 실기에서 같은 관측을 한 것은 아니다.
