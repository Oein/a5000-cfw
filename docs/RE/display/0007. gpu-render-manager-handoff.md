# 0007. GPU render manager / handoff — 라이브뷰 중 우리 UI를 GPU로 ch53에 올릴 수 있는가

- 상태: 정적 RE 종결 (libObj.so 1.10 IDA 덤프 + objdump 교차확인, 에뮬 GPU 모델/문서 `packages/emulator/docs/RE_DISPLAY_GPU.md`, `RE_UI_BRINGUP.md`, `RE_GPU_P3D_CMD.md` 대조). 동적 확인 1건은 §6 실험으로 설계만 했다. 판정은 그 결과와 무관하다.
- 대상: `im.elf` / `libObj.so` 1.10 (rm 드라이버, GRM, DMP 2D, DMP-EGL, dmpNative가 모두 libObj에 정적 링크됨), `grm_gles.ko`
- 참고: ZV-E10 Astra `docs/methodology.md` §2.1 (`g4_handoff_real_device`, `patch_mwf_shadow`)
- 한 줄 판정: **GPU로 ch53 내용을 만드는 것 자체는 가능하다** (in-proc, 스톡 스레드 컨텍스트 불필요, ch51/av-cam 무관). 그러나 **CPU 경로 + Recipe A(`/dev/stream`)보다 실익이 거의 없고**, 우리 렌더러를 GL로 다시 짜야 이득이 생긴다. (a) GRM GPU blit = 가능, 비권장(보조 가속용으로만). (b) 자체 GLES2 컨텍스트 = 가능, 현시점 비권장. (c) ZV-E10식 rm park/seize = **불필요하고 위험, 기각**. 다음 단계는 Recipe A다.

> ⚠️ **선행 문서 정정**
> 1. 0001 §2.1 / 0002 §1의 "순정 OSD는 GPU 없이 CPU가 래스터화한다"는 **틀렸다.** 순정 UX(촬영 화면 포함)는 GLES2로 그려진다. 에뮬 실측(`RE_GPU_P3D_CMD.md` §6~7): 촬영 화면까지 779 draw 중 775개가 640×480 RGBA4 **tiled** 컬러버퍼(gl_common, 에뮬 PA `0x8D7B0500`)에 그려지고, eglSwapBuffers 백엔드가 **PPF(display transfer)로 linear 패널 버퍼 `0x8F758000`/`0x8F7EE000`**에 옮긴 뒤 VDF로 제출된다. 0001이 본 `GRM_bitmapWriteLockBits` CPU 경로는 일부 위젯/스톡 유틸용이고 주 경로가 아니다. (0001의 결론 "GPU 합성으로 갈아탈 이유 없음, 바닥은 매핑"은 아래 §5 이유로 그대로 유효하다.)
> 2. 0005 §1.2의 "경로 B(`gen_struct_for_update` `sub_5DD190`)는 레코드 `+20`에 phys를 쓰지 않는다"는 **Hex-Rays가 r1 인자를 버린 탓**이다. objdump로 보면 `0x5DD224`에서 `r1 = rec+20`을 만든 뒤 `0x5DD22E`에서 `BMP_GetPhysicalAddress`(`sub_589CF8`)를 호출한다. 즉 **경로 B 레코드도 phys가 `+20`에 있다**(에뮬 `RE_DISPLAY_SCANOUT.md` §5 레이아웃과 일치). funcMode 23 문제의 원인은 별도로 다시 봐야 한다(§7).
> 3. 0002 §1의 "`sub_644C80`/`sub_5342B4` = GLES swap commit"은 정확히는 다음과 같다. `sub_644C80`는 DMP-EGL의 native-window 포스트 함수다(EGL attrib 리스트에서 `0x8100` 쌍만 추려 `sub_5DDEEA` → WindowImpl `sub_5DD33C`로 넘긴다). `sub_5342B4`는 Porting_Musashi의 "update frame" 후처리로, `sub_5DB588`("dmpNativeSendWedgeCommands") → `sub_5DD2E4` → UpdateManager `sub_5DCC1C`를 부른다.

## 1. Q1 — render manager(rm) 객체 모델

### 1.1 초기화 3종 (`sub_5E8CD0`가 순서대로 호출, DMP-EGL 초기화 시)

| 함수 | 주소 | 하는 일 |
|---|---|---|
| `rm_reg_init` | `0x5E97F0` | 원자 플래그 `0xEEF20C`로 1회만 실행. `/dev/dmpgles2` open(fd `0xE819FC`), `/dev/mem` open(fd `0xE819F8`). ioctl `0x80048206`(레지스터 크기 0x4000) → `0xEEF210`, ioctl `0xC0048202` idx1(레지스터 PA `0xF1000000`) → `0xEEF200`, `/dev/mem`으로 mmap → 레지스터 VA `0xEEF208`. ioctl `0x80048263`(PSC dummywrite 워크어라운드 플래그, 실기 0) → `0xEEF214` |
| `rm_rqueue_init` | `0x5EA790` | `/dev/dmpgles2`를 0x20000 바이트 mmap(`sub_5EA650`) = grm_gles.ko의 vmalloc **공유 페이지**(프로세스 간 공유: im.elf + Android surfaceflinger의 libDMPSUGIRM). 첫 사용자가 0으로 초기화. 헤더 포인터들을 `0xEEF21C..0xEEF278`에 캐시(count `+16`, head `+4`, tail `+8`, free-hint `+12`, hw-log 상태 `+20..`). 엔트리 배열 = 공유 페이지 `+232`(`0xEEF258`), **800 슬롯 × 140 B**. 이어서 DMP 할당기 풀(`sub_5EDDF0`, 1664 B 노드)을 만든다 |
| `rm_kick_thread_init` | `0x5E91E0` | kick 스레드(진입 `sub_5E9120`) 생성, `_g_rm_thread_exit=0`, atfork류 핸들러 `sub_5EBAB0` 등록 |
| 해제 | `sub_5E8D00` → `sub_5E9260`(exit 플래그+깨우기+join) → `sub_5EA760` → `rm_reg_exit` `0x5E9730`(munmap 2개, close 2개) | |

### 1.2 rqueue 엔트리 (140 B = 12 B 링크 헤더 + 128 B 요청)

- 헤더: `+0` used byte, `+2` 우선순위 byte, `+4` next idx, `+8` prev idx.
- 요청(128 B) 공통: `+0` flags(bit0 = 동기/fence 대기, bit1 = skip, bit2/0x80 = hw-log), `+4` **type**, `+8` 소유 **pid**, `+12` tid, `+28..+36` 완료 콜백 배열/개수, `+40..+44` EGL sync 리스트, `+60..` 엔진별 페이로드.
- 넣기: `sub_5EAA60`(일반 128 B 요청 n개; 래퍼 `sub_5E8D20`이 큐가 가득 차면(반환 1) 1 tick 쉬고 재시도), `sub_5EAE20`(PPF용 92 B 디스크립터 → type 2 요청으로 변환). 둘 다 공유 세마포어 1(ioctl `0xC0048211`/`0xC0048212` = mlock gain/release) 아래에서 링크를 갱신하고, 큐가 비어 있다가 채워지면 `sub_5E9250`(ioctl `0xC004820E`, signal)로 kick 스레드를 깨운다.
- 빼기: peek `sub_5EB350`, pop `sub_5EB280`, 처리 `sub_5EB820` → 실행 `sub_5EA170`.

### 1.3 kick 스레드 `sub_5E9120`

세마포어 2를 잡고 큐 head를 peek한다. head의 pid가 **자기 pid면** 처리하고(GPU suspend 중이 아니면 `sub_5EB820`), **남의 pid면** 그 pid에게 ioctl `0xC004820E`로 신호를 보내고 자신은 ioctl `0xC004820D`로 잠든다. 즉 **각 프로세스는 자기 요청만 자기 kick 스레드에서 실행**한다. GPU는 프로세스 간 시분할되고, 순서는 공유 큐가 보장한다. 신호 대상 pid가 없으면(반환 `0x1FFFFFFF`) 그 요청을 버린다.

### 1.4 실행 `sub_5EA170` — 엔진별 레지스터 기록 (`/dev/mem` 매핑에 직접 MMIO)

| type | 엔진 | 기록 | 완료 대기(`sub_5EA030` → ioctl `0xC0048203`) |
|---|---|---|---|
| 1/7/8 | P3D 커맨드 리스트 | `sub_5E9F90`: `+0x1804`=리스트 주소, `+0x1800`=크기(킥) | bit31 |
| 2 | PPF display transfer / texture copy | `sub_5E9E00`: `+0xC00` src>>2, `+0xC04` dst>>2, `+0xC08/+0xC0C` 크기, `+0xC10` flags, `+0xC18` 트리거(`flags&8`이면 `+0xC20..C28` copy 모드). w 또는 h<32이면 CPU 타일러 `sub_5E92E0`로 대체 | bit30 |
| 3 | PSC memory fill | `+0x10` start>>3, `+0x14` end>>3, `+0x18` 값, `+0x1C` ctrl | bit26 |
| 6 | **eglSwapBuffers 백엔드** `sub_5EBFA0` | begin_swap → (P3D quad) → PPF(tiled 컬러버퍼 → linear native-window 버퍼) → end_swap → dmpNative update | bit31/bit30 |
| 9/10 | HW bypass on/off | ioctl `0xC004820F` | — |

완료 후 EGL sync 리스트를 `EGL_SIGNALED_KHR`(0x30F2)로 바꾸고 콜백을 호출한다. **GPU가 직접 쓰는 fence는 없다.** 완료는 IRQ 76 → grm_gles `int_status` → ioctl 반환 경로로만 온다. ioctl 대기는 3000 jiffies 타임아웃이고, 타임아웃이 나면 커널이 GPU를 리셋한다.

### 1.5 ioctl ABI (`grm_gles.ko`, magic 0x82, 인자 u32 1개) — 에뮬 `RE_DISPLAY_GPU.md` §2.2와 교차확인

`0x80048206` 레지스터 크기 / `0xC0048202` bar PA / `0xC0048203` IRQ 대기(mask & 0xC4000000) / `0xC0048208`·`0xC0048209`·`0x8004820A` suspend·resume·suspended? / `0xC004820D`·`0xC004820E` pid별 wait·signal / `0xC004820F` bypass / `0xC0048211`·`0xC0048212` 공유 세마포어[0..2] down·up / `0x80048263` 워크어라운드 플래그. mmap 길이 0x4000이면 레지스터, 0x20000이면 공유 페이지. **커맨드 제출은 ioctl이 아니라 유저공간 MMIO**다. 커널은 클럭, IRQ ack, 세마포어, 공유 페이지만 맡는다.

## 2. Q2 — GRM / DMP 2D API 표면 (CPU lock 외에 GPU 연산이 있다)

계층: **GRM gperm**(비동기, 큐+워커) → **DMP_2D**(동기, 전용 스레드 + 전용 EGL 컨텍스트) → **DMP GLES2** → rm 큐.

**RectBlit 인자 레코드**(GRM 쪽, 80 B; 스톡 호출자 `sub_531278` = `GraphicsDraw_musashi.cpp` drawBitmap에서 복원): `+0` src BMP, `+4` src (left,top) s16×2, `+8` src (right,bottom), `+12` dst BMP, `+16` dst (x,y), `+20` dst (x2,y2), `+24/+28` dst 클립, `+32` 1=copy / 2=alpha blend, `+36` 전역 알파 byte(0xFF), `+48` bit8 = 스케일 사용, `+60/+64` 스케일 x/y(float). 스톡은 **포맷 4(A8)끼리면 memcpy, 그 외는 GPU blit**을 쓴다. 즉 순정 UX의 비트맵 그리기는 GPU다.

**DMP_2D 검증 제약**(`sub_63D820`): 베이스 128 B 정렬, 폭·높이 8의 배수(640×480 OK), src DMP 포맷 ∈ {0,1,2,3,7}, dst ∈ {0,1,7}, blend flags는 하위 6비트만.

|---|---|---|---|

| 2, 8 | 4 | 1 | DMP 고유 internal `0x8000` / UNSIGNED_BYTE (32 bpp, 바이트 순서 [?]) |
| 3 | 2 | 2 | YCbCr 4:2:2 (`0x8A1F`/`0x85BA`) — src 전용 |
| 4 | 1 | 3 | GL_ALPHA (A8) — src 전용 |
| 9 | 4 | 7 | GL_RGBA / UNSIGNED_BYTE |

**GPU가 물리 버퍼에 직접 렌더하는 메커니즘**(`sub_63C700`): 텍스처를 바인드하고 DMP 텍스처 파라미터 `0x6002`=1(텍스처 객체 `+50`), `0x6003`=bitmap 속성(`+52`, linear/block 계열 [?])을 설정한 뒤, `glTexImage2D`(`sub_61A100`)의 pixels 자리에 **물리주소**를 넘기고 `glFramebufferTexture2D`(`sub_61D1E0`, COLOR_ATTACHMENT0)로 붙인 다음 `glCheckFramebufferStatus`(`sub_61EE10`)==COMPLETE를 확인한다. 즉 **zero-copy로 임의 물리 버퍼를 렌더 타깃/텍스처로 쓰는 DMP 확장**이 있다. `0x6002`=phys 모드라는 해석은 호출 문맥에서 추론한 것이다 [?].

**DMP_2D EGL 컨텍스트**(`sub_63C600`): `eglGetDisplay(1)` `sub_5F2B70` → `eglInitialize` `sub_5F2BE0` → `eglChooseConfig` `sub_5F3300`(RGBA8888, ES2, PBUFFER) → `eglCreatePbufferSurface` `sub_5F4AB0` → `eglCreateContext` `sub_5F6470`(ES2) → `eglMakeCurrent` `sub_5F6C00`. 셰이더는 프리컴파일 바이너리를 쓴다(`sub_6186C0`, 유니폼 `u_texMatrix/u_color/u_colorMatrix/u_alpha/u_scale/u_offset/u_sampler`). EGL/GL 심볼은 전부 stripped라 오프셋으로만 부를 수 있다.

## 3. Q3 — 순정 OSD는 어떻게 GPU 렌더되어 ch53에 도달하나

```
appFw 메인루프 sub_702E3C → "draw" sub_70CD64 → ux gfxeng(GraphicsDraw_musashi: GRM gperm blit/fill, GL)
   → Rigel WindowClient post → Rigel WS(gs 스레드, sub_67BBB8) 합성 (GLES)
   ── 대부분의 draw는 640×480 RGBA4 tiled EGL 컬러버퍼(gl_common)로 ──
eglSwapBuffers → rm 요청 type 6 (sub_5EBFA0, kick 스레드에서 실행)
   ① begin_swap (WindowImpl sub_5DD3DC; 직전 프레임 VDF ack까지 UpdateManager 락 대기)
   ② PPF display transfer: tiled RGBA4 컬러버퍼 → linear native-window 버퍼   ★ GPU가 ch53 버퍼에 쓰는 지점
      (에뮬 실측 PPF flags 0x4401 = in/out RGBA4 + flip, dst = 0x8F758000 / 0x8F7EE000 교대)
   ③ end_swap sub_645BE0 → sub_644C80 → sub_5DDEEA → WindowImpl sub_5DD33C
      → FbContainer::gen_struct_for_update sub_5DD190 (record +20 = BMP_GetPhysicalAddress = 위 linear 버퍼)
      → UpdateManager sub_5DCC1C (게이트 sub_5DCAB4) → vdf_if_port_send_update sub_5DC3D4 (osal 0x80003B type 5)
   → dmpNative CmdQueue → OSDPin 0x59000E → av-cam VDF → VPH ch53 +0x20
```

- **ch53이 가리키는 버퍼 = dmpNative FbContainer 원소 버퍼(더블 버퍼, RGBA4444 linear, stride 1280)**이고, GPU는 그 버퍼에 **PPF로만** 쓴다(3D 렌더는 tiled 중간 버퍼에 한다). 0003/0004가 관측한 ch53 토글 `0x8f7ee000`↔`0x8f758000`이 바로 이 두 버퍼다.
- SenserIf(`sub_5D99D0`)는 `getResponse` 가상함수다. 외부 OSAL 요청에 응답해 grm_sens_work를 1회 제출하며 주 렌더 경로가 아니다.
- 우리 detour-swap(0002)이 촬영에서 바꾸는 `+20`은 **이 eglSwap 경로 레코드의 PPF 목적지 phys**다. 그래서 swap이 이기는 동안에도 순정 GPU 파이프라인은 매 프레임 순정 버퍼에 계속 PPF를 쓴다. 이 비용은 사라지지 않지만 우리에게 해는 없다.

## 4. Q4 — 벡터별 판정

### (a) in-proc에서 GRM GPU blit으로 우리 버퍼를 ch53 서피스에 합성 — **가능 / 보조 가속용으로만, 지금은 비권장**

- 경로: 우리 워커 스레드에서 `BMP_CreateFromPhys`(`0x589A00`)로 src BMP(GRM 9 RGBA8888, 또는 GRM 1 RGBA4444)와 dst BMP(GRM 1, 640×480, phys = detour로 latch한 우리 ch53 버퍼)를 만들고 `GRM_gpermRectblit`(`0x5560B0`)를 호출한다. 실제 GL 작업은 **스톡 GRM CmdWorker → DMP_2D 실행 스레드**(자체 EGL 컨텍스트)가 하므로 **호출 스레드 친화성 제약이 없다**. `vdf_if_port_send_update`처럼 특정 스톡 스레드에서만 동작하는 제약이 없다.
- 전제: GPE 매니저가 기동 상태여야 한다(`sub_555564()+4` byte==1, 아니면 -2). `grm_init`이 부팅 시 켜고 `grm_sus`(`0x556CEC`, Android 월드 스위치 등)가 끈다.
- 위험:
  - 인자 오류는 대부분 `__assert_fail` → **im.elf abort**(실기 재부팅 필요)다. `sub_63D820`의 -5 검증이 일부만 거른다.
  - DMP_2D는 TLS 재진입 가드(`0xEF515C`)가 있어 **DMP_2D 콜백 안에서 다시 부르면 -3**을 낸다.
  - dst BMP 쓰기 lock을 명령 끝까지 잡으므로, 우리가 같은 BMP를 CPU lock 중이면 교착된다. → dst는 GPU 전용으로 쓴다.
  - 스톡 UX와 같은 rm 큐(800 슬롯)를 공유하므로 큐 경쟁은 있지만 정상 동작 범위다.
- ch51/av-cam: **무관**. GPU(PA `0xF1000000`)는 VPH/VDF와 별개 IP이고, VDF 제출은 하지 않는다. DDR 대역 경쟁만 미미하게 생긴다.
- 실익: src를 여전히 CPU가 그리므로 절약되는 것은 RGBA8→4444 변환 + 버퍼 쓰기뿐이다. Recipe A 이후 그 비용은 프레임당 수 ms 이하다(§5). 반면 왕복 지연(GRM 큐 → CmdWorker → DMP_2D cond 핸드오프 → GL → rm 큐 → kick → IRQ, 필요하면 PPF까지 IRQ 1회 더)이 추가된다. **결론: 전체 화면 페이드/스케일/알파 합성 같은 대면적 효과에만 의미가 있다.**

### (b) GLES2로 우리 UI를 GRM/물리 서피스에 렌더 — **가능 / 현시점 비권장(렌더러 재작성 필요)**

- 방법 1(권장 형태): **우리 전용 스레드 + 전용 EGL pbuffer 컨텍스트.** DMP_2D(`sub_63C600`)와 같은 6단계 EGL 시퀀스로 만들고, 렌더 타깃 = 우리 ch53 phys를 `0x6002`/`glTexImage2D(phys)`/FBO로 붙인다(`sub_63C700` 레시피). DMP-EGL은 프로세스 안에 여러 컨텍스트를 이미 운용한다(Rigel WS, ux gfxeng, DMP_2D). 컨텍스트는 스레드 TLS(`sub_6183D0`)에 묶이므로 **한 스레드에서만 make-current/draw**해야 한다.
- 방법 2(비권장): 기존 detour(스톡 VDF 제출 스레드 = kick/dmpNative 경로) 안에서 GL을 호출하는 것. 그 스레드에는 우리 컨텍스트가 current가 아니다. make-current를 바꾸면 스톡 컨텍스트 상태를 오염시킨다. 게다가 type 6 실행 중(kick 스레드 내부)에 GL을 부르면 rm 큐 재진입으로 **자기 kick 스레드를 기다리는 교착**이 생길 수 있다. → **금지.**
- 타일링: P3D 컬러버퍼는 PICA 계열처럼 8×8 tiled, 원점이 아래쪽이다. 순정은 tiled에 그린 뒤 PPF(flip, RGBA4→RGBA4)로 linear에 옮긴다. 따라서 linear ch53 phys에 직접 렌더할 때 `0x6003`이 linear 렌더를 보장하는지는 **정적으로 확정되지 않았다**. 확정은 §6 실험 E1에서 한다. 안전한 대안은 순정과 똑같이 하는 것이다. tiled 중간 버퍼에 렌더한 뒤 DMP_2D_DisplayTransfer(`sub_63D960`, 포맷 코드 7 = RGBA8→RGBA4 또는 10 = RGBA4→RGBA4, 모드 0 = tiled→linear)로 ch53 phys에 옮긴다. 이 경로는 순정 실측과 동일하므로 동작이 보장된다.
- 실익: 우리 UI 래스터화(텍스트 글리프, 사각형, 알파)를 GPU로 옮길 때만 생긴다. 현재 uicore는 CPU Canvas이므로 **글리프 아틀라스 텍스처 + 쿼드 배치 렌더러로 재작성**해야 하고, Track A 골든과의 픽셀 패리티도 다시 맞춰야 한다. ch51/av-cam에는 무관하다. 크래시 위험은 GL 오류 시 대부분 GL 에러 코드로 끝나지만, EGL 초기화 실패나 잘못된 phys를 텍스처에 쓰면 메모리 오염 → im.elf 크래시다.

### (c) ZV-E10식 rm park/seize — **기각**

- ZV-E10 `g4_handoff_real_device`가 하는 일: Gen4 rm(`rm_exit`, kick 스레드, rqueue)을 세워 `/dev/dmpgles2`와 VRAM을 놓게 한다. 이는 **두 번째 Sony UI 스택(Gen5 libOb5/appFw)을 같은 장치에 올리기 위한 것**이고, `patch_mwf_shadow`(libMWF `0x2d2ac` 분기 nop), `__assert_fail`/`abort` 무력화, cond-wait 2초 강제 해제 같은 응급 패치를 함께 쓴다. 우리 목적(우리 콘텐츠를 ch53에)과 다르다.
- a5000에서 불필요한 이유:
  - rm은 이미 **멀티프로세스·멀티컨텍스트**다(공유 페이지 큐 + pid별 kick, §1.3).
  - 우리는 im.elf **안**에 있어서 같은 드라이버를 그대로 쓸 수 있다((a)/(b)).
  - 독점권을 얻어도 패널 도달은 여전히 VDF 레코드(detour)로만 가능하다. GPU 독점은 ch53 접근권을 주지 않는다.
- 위험(치명적): rm을 세우면 스톡 GL 사용자 전부(Rigel WS, ux gfxeng, DMP_2D, Android surfaceflinger)의 요청이 처리되지 않는다.
  - 다음 eglSwap의 begin_swap/EGL sync 대기, 또는 DMP_2D `sub_6402A0`의 cond_wait에서 **appFw 메인루프와 gs 스레드가 영구 정지**한다.
  - 그 결과 스톡 이벤트 처리(셔터·모드·SDCom 응답)가 멈추고 워치독 위험이 생긴다.
  - kick 스레드를 죽이면 공유 큐 head가 우리 pid로 남는다. 그러면 surfaceflinger의 kick 스레드가 우리에게 신호만 보내고 영원히 잠든다(§1.3, 교착).
  - 3000 jiffies 타임아웃이 나면 커널이 **GPU 리셋**을 하여 진행 중인 스톡 프레임이 깨진다.
  - ch51 자체는 GPU와 무관하지만 UI와 카메라 제어가 멈춘다.

## 5. Q5 — 현재 CPU 경로(Recipe A) 대비 실익 추정

| 항목 | CPU + `/dev/mem`(현재) | CPU + `/dev/stream`(Recipe A, 0006) | GPU (a) blit | GPU (b) 전면 GL |
|---|---|---|---|---|
| 전체 프레임 기록(640×480×2 = 600 KB) | ~75 ms(실측 바닥 ~8 MB/s) | write-combining으로 수십 배 → **수 ms** | CPU 기록 0, 대신 src 래스터는 CPU 그대로 | 0 |
| 메뉴 1스텝(dirty 행 위주, 수십 KB) | 수 ms | **< 1 ms** | 큐 왕복 지연(추정 1~3 ms, 미측정) + GPU 시간 | 같은 왕복 + 렌더러 오버헤드 |
| 구현 비용 | — | 문자열 한 줄 + 배리어 | 중간(BMP 2개 + 콜백 + 오류 처리) | 큼(렌더러 재작성 + 패리티) |
| 위험 | — | 낮음(폴백 있음) | assert = im.elf abort | EGL/메모리 오염 |

- 결론: Recipe A 이후 남는 CPU 비용은 래스터화 자체(텍스트·도형)와 dirty 영역 쓰기뿐이고, 메뉴 반응성(0002: 키→가시변화 0.18 s, 순정 0.28 s)은 이미 순정 이상이다. GPU (a)는 그 위에서 **"변환+쓰기" 수 ms 이하만** 줄이면서 지연을 더한다. **실질 이득 ≈ 0.** GPU (b)는 렌더러를 GL로 바꿔야 래스터 비용이 없어지는데, 640×480 2D UI 수준에서 그 비용 역시 프레임당 수 ms이고 재작성 비용과 위험이 압도적으로 크다.
- GPU가 의미 있어지는 조건: 전체 화면 알파 페이드, 이미지 스케일(재생 썸네일·확대), 30 fps 애니메이션처럼 **대면적 픽셀 처리**가 생길 때다. 그때는 (a)의 `GRM_gpermRectblit`(알파/스케일 지원)를 국소 가속기로 붙이는 것이 비용 대비 최선이다.

## 6. 동적으로만 확정되는 것 + 에뮬 실험 설계 (판정은 결과와 무관)

에뮬 GPU 모델 `qemu-overlay/hw/display/dmp_smaph.c`가 P3D/PPF/PSC를 기능적으로 실행하므로 정합성은 에뮬에서 확정할 수 있다. 단, 소프트웨어 래스터라서 **성능(지연·처리량)은 에뮬로 측정할 수 없다.**

**E1 — GRM RectBlit을 linear RGBA4444 dst에 쓸 때의 정합성**(테스트 전용 .so, 스크래치에서 빌드, production 코드 미수정)
1. a5kinject로 im.elf에 주입한다. 워커 스레드에서 `utilGetMemory`(`0x5D9AEC`) 2회로 src(640×480×4)와 dst(640×480×2) phys 버퍼를 확보한다. src를 `/dev/stream`으로 매핑해 4분면 패턴(불투명 R/G/B + 반투명 영역)을 채운다.
2. `BMP_CreateFromPhys(640,480, fmt=9, …, src_phys, 640, &rect, &srcBmp, 0, 0)`, 같은 방식으로 `fmt=1`, `dst_phys`로 dst를 만든다.
3. §2 레이아웃으로 RectblitArgs를 채운다(copy 모드 `+32=1`, 전역 알파 0xFF, 전체 rect). 콜백에서 완료 시각을 기록하고 `GRM_gpermRectblit(&req, NULL, &args, cb, ctx)`를 호출한다.
4. `-trace dmp_smaph_job`으로 확인할 것: P3D draw 1건의 target = dst_phys인지, 추가 PPF가 있는지. HMP `pmemsave dst_phys 614400`으로 덤프한다.
5. 통과 기준: 덤프를 RGBA4444 linear(위→아래)로 디코드하면 패턴과 일치해야 한다. 상하 반전이나 8×8 블록 스크램블이 보이면 `0x6003`이 linear 렌더를 보장하지 않는다는 뜻이다. 그 경우 (b)의 "tiled 렌더 + DisplayTransfer(모드 0, flip)" 경로가 정답이다.
6. 부가 측정: 호출→콜백 사이 rm 큐 요청 수(type 1 몇 건, type 2 유무)를 센다. 이것이 실기 지연을 추정하는 근거(IRQ 왕복 횟수)가 된다.

**E2 — DMP_2D_DisplayTransfer 직접 호출**(E1이 실패할 때만): op 5, 포맷 코드 10(RGBA4→RGBA4), 모드 0, flip 플래그. 순정 swap과 동일한 경로라 성공이 예상된다.

실기 전용 항목: 큐 왕복 지연의 절대값(ms). 판정(Recipe A 우선, GPU 비권장)은 이 값이 1 ms이든 3 ms이든 바뀌지 않는다.

## 7. 귀결과 다음 단계

1. **다음 단계 = Recipe A(0006) 적용 + 실측.** GPU 경로는 착수하지 않는다.
2. GPU가 필요해지면(대면적 효과) (a) `GRM_gpermRectblit` 국소 가속부터 시작한다. 그 전에 E1으로 linear dst 정합성을 확정한다.
3. (c) rm park/seize와 ZV-E10식 handoff는 영구 기각한다.
4. **별건 재조사 필요**: 0005의 funcMode 23 근본원인 서술 중 "경로 B는 `+20`에 phys가 없다"는 정정되었다(§0 정정 2). 23에서 swap이 안 먹는 진짜 이유는 다음 후보 중에서 레코드 덤프(이미 있는 hook instrument)로 다시 확정해야 한다: (i) 레코드 지오메트리/개수가 isPanel 조건과 다름(n=2 레코드, 부분 rect), (ii) 23 뷰가 다른 FbContainer(`+200`)나 다른 bpp를 씀, (iii) 더블버퍼 교대로 latch가 덮임. 0005의 수정 방향(DISP 소비로 23 진입 차단, `mgr+100`)은 원인과 무관하게 유효하다.
