# 0002. InfraDial 다이얼 회전 처리 파이프라인

> 상태: 구조·타이머 모델 **derived**(libObj 정적, 높음). 방향 판정은 **2026-11-19 실기 로깅으로 정정**(아래 §3). 대상: libObj.so 모듈 기준 주소.

## 1. 요약

컨트롤 휠의 회전은 키 이벤트(createEvent)와 다른 경로다. 순정은 연속 인코더 값을 `InfraDial`이 "리딩엣지 래치 + 속도적응 무시창"으로 이벤트화한다. 네이티브(Diadem) 모드에서는 이 이벤트가 evdev/createEvent로 나가지 않기 때문에, 커스텀 UI는 `sub_710370`을 직접 가로채야 한다.

## 2. 콜백 등록과 레코드

`InfraDial` 생성자(`sub_710F4C` @0x710F4C)가 OSAL 큐 콜백 3개를 등록한다.

| 큐 id | 콜백 | 역할 |
|---|---|---|
| 0x11B02AA (18547370) | `sub_710370` | **다이얼 회전 이벤트 입구** |
| 0x11B02A9 | `sub_70FB14` | SetDialEventInterval 설정(UIPC) |
| 0x11B02A8 | `sub_710070` | 테스트 커맨드(동기) |

회전 이벤트를 보내는 생산자는 libObj/im.elf에 없다(물리 드라이버/보조코어 측). 쿼드러처 디코딩 규칙은 정적으로 볼 수 없다.

페이로드(`InfraDialEventDataRecord`, 12B):

| 오프셋 | 필드 | 타입 | 의미 |
|---|---|---|---|
| +0 | local_key_code | u32 | 논리 키. 실측상 **양방향 모두 같은 값(22)** |
| +4 | degree_per_sec | s32 | **부호 있는 각속도. 방향은 이 값의 부호** |
| +8 | ex_info | s32 | 보조 정보, 하류로 그대로 전달 |

## 3. 방향 판정 — 정정 기록

초기 정적 해석은 "CW/CCW는 별개의 local_key_code(2코드)이고 degree 부호는 속도 전용"이었다. 실기(2026-11-19)에서 훅으로 원시 값을 찍은 결과 **반증**되었다.

- `a1[0]`(local_key_code)은 CW/CCW 모두 22로 고정 — 방향을 담지 않는다. 즉 "1코드 + 부호" 설계가 실제.
- 방향 = `a1[1]` 부호. CW는 `{+n, 0}`만, CCW는 `{-n, 0}`만 나오며 부호가 가짜로 뒤집히지 않는다.
- 유일한 노이즈는 `a1[1]==0`(디텐트 영점 교차, 방향 정보 없음). 기존 구현이 `deg>=0 ? CW : CCW`로 이 0을 CW로 오판해 CCW 클릭마다 유령 CW가 섞였고, 이것이 "방향 반전" 버그의 원인이었다.
- **수정(구현·실기 검증 완료)**: `a1[1]==0`은 무시, 방향은 `sign(a1[1])`, 같은 방향 반복은 디텐트 시간창 디바운스, 방향 반전은 즉시 방출. 환경 변수로 CW/CCW를 스왑하는 옵션을 두어 다른 바디(a6400) 포팅에 대비. 결과: 느린 클릭은 클릭당 1스텝, 빠른 스핀은 순수 단일 방향, 반전 누출 0.

순정 코드의 구조(맵·리딩엣지·타이머)에 대한 아래 설명은 여전히 유효하다.

## 4. 순정 `sub_710370`의 동작

1. 세마포어 188을 잡고, 인스턴스의 `dial_event_map`(this+36, key=local_key_code)에서 레코드를 찾는다. 레코드가 가리키는 `InfraInputPhyKeyData`(16B)의 status/ex_info를 새 값(degree_per_sec/ex_info)으로 덮어쓴다 — 하류로 나가는 바이트가 바로 이것.
2. `|degree_per_sec|`이 0이 아니면 간격 `v17 = max(1000*maxInterval, 1000*minInterval)`(µs)을 계산한다. 개별 설정 플래그가 있으면 그쪽 값, 없으면 인스턴스 기본값(this+60/62/64).
3. **리딩엣지 판정**: 해당 엔트리의 `scheduled` 플래그가 0이면 `sub_71BAA8`로 1스텝을 즉시 방출(출력 큐 `dword_7A0020`), `scheduled=1`로 바꾸고 v17 타이머를 건다. 이미 1이면 아무 것도 하지 않는다(= 최신 degree만 갱신하고 **스왈로**).
4. 타이머 콜백(`sub_70F4B8` @0x70F4B8): 재방출(자동 반복) 후, 마지막 degree가 0이 아니면 다시 타이머를 건다(빠르게 돌수록 간격이 짧아져 스텝 증가). 0이면 멈춘다 — 멈출 때 드라이버가 degree=0 이벤트를 1회 보낸다.
5. 재개(`sub_710E38` @0x710E38)는 모든 엔트리의 `scheduled`를 0으로 초기화한다. 주입 코드도 재개/재주입 시 같은 초기화가 필요.

핵심: "디텐트 1개 = 이벤트 1개"는 이 계층에 없다. 연속 인코더를 각속도 스트림으로 바꾼 뒤 무시창으로 흔들림을 흡수한다.

## 5. 하류 라우팅

회전 이벤트 → 큐 0x11B02AA → `sub_710370` → `sub_71BAA8` → 공통 InfraInput 출력 큐(`dword_7A0020`, InfraHotshoe 등도 공유) → `snd_InfraInputEvent_to_InputServant`(@0x37F2D4).

- 이 마지막 함수는 `IsViewModeDiadem()==0`(= Android 앱 모드)일 때만 24바이트를 InputServant 큐(21627945)로 보낸다. **네이티브/Diadem 모드에서는 여기서 끝**이라 evdev/createEvent로 나오지 않는다.
- 앱 모드에서 InputService가 key_code를 스캔코드(525/526)로 바꾸고 `createEvent`(@0x37F854)로 위젯에 전달한다. 525/526은 따라서 **앱 모드 경로의 코드**다.
- route-b(네이티브 모드)는 `sub_710370`을 디투어해서 `osal_free_msg` 후 반환(순정 이중 처리 차단)하는 방식으로 다이얼을 얻는다.

## 6. 신뢰도 표

| 항목 | 신뢰도 |
|---|---|
| 콜백 등록·레이아웃·세마포어·방출 큐 | 높음 (디컴파일 + 디버그 문자열) |
| 리딩엣지 + 속도적응 반복 모델 | 높음 |

| 상류 생산자(0x11B02AA 송신자) | 미확인 (드라이버/보조코어) |

## 7. 운영 노트 (Android 앱 쪽)

휠 랙 이슈: 커널은 다이얼을 event0로 약 20회/초 내보내지만, ScalarInput 경로(`onCameraKeyDown`)는 프레임워크 페이싱으로 약 7회/초만 전달한다. 앱은 `/dev/input/event0`을 백그라운드 스레드에서 직접 read해 해결(측정: 10초 179이벤트, 3:1 코알레싱, 멈추면 최종 위치로 점프). 앱 uid가 input 그룹이 아니므로 시작 시 root 셸로 `chmod 666 /android/dev/input/event0`를 실행한다(tmpfs라 재부팅하면 원복, 벽돌 위험 0).
