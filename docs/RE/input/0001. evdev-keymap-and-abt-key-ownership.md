# 0001. evdev 키맵과 ABT 키 소유권

> 상태: 키맵 **observed**(실기 3회 캡처), ABT 메시지 레이아웃 **derived**(정적, 높음), 휴지통/Fn/DISP 코드 **미확정**.

## 1. 입력 경로 한눈에

a5000의 물리 키는 `im.elf`가 `/dev/uinput`으로 만든 가상 evdev 장치(이름 "D keyboard", `/dev/input/event0`)로 흘러나온다. Android의 system_server가 이 장치를 읽는다(grab이 아니라 병렬 읽기 가능). 즉 네이티브/앱 어느 쪽이든 event0를 직접 읽으면 키를 받을 수 있다.

- 레코드: 표준 `struct input_event` 16바이트(sec/usec/type/code/value), type=1(EV_KEY), value=1 눌림 / 0 뗌.
- **EV_KEY code가 곧 Sony ISV_KEY 스캔코드**다. 중간 변환표가 없다. 근거: 앱 쪽 키 분기가 `getScanCode()` 값을 `ISV_KEY_*` 상수와 바로 비교하고, JNI 콜백(libandroid_servers의 `ISV_KeyEvent_cb`)이 코드를 리맵 없이 그대로 전달한다.

- 휴지통(삭제) 버튼: 초기 노트의 "530 추정"은 캡처 시작 전에 눌린 키의 꼬리(눌림 없는 뗌 이벤트)였던 **아티팩트**로 판명. 실제 코드(ISV_KEY_DELETE)는 아직 캡처하지 못했다.
- 미캡처: Fn, C(커스텀), DISP, SK1/SK2, ISV_DIAL_1/2. 전경 앱이 키를 모두 받는 상태에서 버튼을 하나씩 따로 눌러 1회 재캡처 필요(다이얼/키 ISV 상수는 sysutil의 ScalarInput odex를 디오덱스하면 교차 검증 가능).
- 자체 메뉴 코드에서 쓰는 보조 정보: createEvent(네이티브 모드) 키 이벤트 id는 `0x15010000 | code<<4 | edge` 형태이며 센터/4방향/MENU/PLAY의 내부 코드는 0x06/0x07/0x08/0x0a/0x09/0x11/0x0f. 줌(0x22/0x23)은 노이즈가 섞여 무시한다. 다이얼 회전은 이 표에 없고 별도 경로다([0002](0002.%20infradial-dial-pipeline.md)).

## 3. 왜 어떤 앱에서는 휠 키만 오는가 (ABT 통지)

실측: OpenMemories Tweak 실행 중에는 휠 계열(103/108/105/106/232/525/526)과 MENU 일부만 event0에 보이고, MENU·셔터·MOVIE·재생·줌은 오지 않았다. ILCE Remote 실행 중에는 전 키가 왔다. 차이는 앱이 `onResume`에서 `AppInfoReceive` 브로드캐스트를 보내는지 여부다.

체인(정적 확정):
1. 앱 → `com.android.server.DAConnectionManagerService.AppInfoReceive` 브로드캐스트.
2. 서비스(Java) → JNI `libandroid_servers.so`의 notifyAppInfo(실제 호출부 `sub_21B0F82C`, 파일 오프셋 0xFA1C 부근).
3. JNI → `ABT_set_state(3, X, NULL, NULL, NULL, keyinfo, 0x98)` (`libarbiter_proxy.so` `ABT_set_state_0` @0xB74).
4. 프록시 → OSAL 큐 `0x01490411`로 **436바이트(0x1B4)** 메시지 송신. 서버는 `/usr/lib/arbiter.so`(범용 중재기).

메시지 페이로드(436B):

| 오프셋 | 필드 | 값/의미 |
|---|---|---|
| 0x000 | cmd | **3 = ABT_CMD_APP_INFO** (enum: 1=SET_D, 2=SET_A, 3=APP_INFO, 4=EXIT, 5=EXIT_CMP, 6=BOOT_CMP) |
| 0x004 | flag "X" | 카테고리 비트마스크. 정확값 미확정(0x00020002 정도로 충분할 것으로 추정, 미검증) |
| 0x008 / 0x088 / 0x108 | pkg / cls / key (각 128B) | 실제 경로에서는 NULL |
| 0x188 | keyinfo[10] | **키 소유 비트마스크** — 전키 소유는 `{0xFFFFFFFF x4, 0x7FFFDFFF, 0 x5}` |
| 0x1B0 | a7 | 0x98 (메시지 헤더 워드에도 동일 값) |

keyinfo는 비트 인덱스가 키 테이블 값이다(S1_1=1, S1_2=2, S2=3, PLAY=4, MODE_DIAL=5, MOVREC=6, MENU=7, USB=8, AFMF=12, FOCUSHOLD=13 …, 전원 계열은 0x8C 이후). resume 경로는 앞 5워드를 0xFFFFFFFF로 채운 뒤 워드4에서 bit31/13만 지우는 방식으로 "전키 소유"를 표현한다. 개별 키를 명시하는 pkey 경로(`keyinfo[0]=0xFFFFF001`)는 쓰지 말 것.

arbiter 쪽 카테고리(type) 테이블은 `ABT_CAT_PB/USB/OFF/REC`. 패키지 문자열이 아니라 cmd/sender로 Android 앱을 식별하는 것으로 보인다.

## 4. 미확정 / 다음 프로브
- 네이티브 프로세스가 같은 436B 메시지를 직접 보내도 전키가 열리는지(`ABT_PRXY_init()` 후 호출). 휠만 오면 X 값 변주, 그래도 실패하면 `im.elf` 쪽 키 리소스 등록 선행 여부 조사.
- X의 정확한 카테고리값, a7=0x98의 서버측 검증 의미(0x98을 그대로 복제 권장).
- 휴지통/Fn/DISP/C/SK 코드 재캡처.
