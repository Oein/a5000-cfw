# 0001. RE 범위(surface)와 근거 원장

> 방법론: 모든 주장에 **근거**와 **신뢰도**를 붙이고, 모르는 것은 `unknown + 다음 프로브`로 남긴다. 신뢰도: `observed`(실기 관찰) · `derived`(바이너리/데이터에서 직접 도출) · `inferred`(추정).

## 목표 아키텍처 (결정)
```
[우리 UI 프로세스] -- Rigel WindowClient(UX_DEBUG_CLIENT) --> im.elf Rigel Window Server --> 패널/EVF/HDMI
      |  ^ evdev(event0) + ABT 상태(arbiter)
      +-- SDCom(0x1540432) --> im.elf ScalarDaemon --> 카메라 엔진 (라이브뷰 = VDF 영상 평면)
```

## 원장의 주요 항목 (요약)
원장은 약 24건(id L001~)으로, `surface / 주장 / 신뢰도 / 근거 / 다음 프로브` 구조다. 핵심 observed:
- SDCom 연결·GetParameters(116개)·ShiftShutterSpeed 왕복 (L001~L003)
- evdev 키코드 전체 (L004), 공장 WBI 상시 재개 (L010)
핵심 derived:
- 전키 전달 조건 = AppInfoReceive → ABT_set_state(3,…,0x98) (L005)
- 최상위 합성기 = im.elf Rigel Window Server, SF는 한 클라이언트 (L006), Rigel 채널 큐 표 (L007), 창 버퍼 = MA 전역 공간 (L008)
- 147개 명령 처리기 요청 형식 (L012), 이벤트 이름표 81개 (L015), 구독 방식 (L016)
- Display 팩토리(0x0600~) / Movie 팩토리(0x3000~) / Caution / UI 설정 조회 (L018~L021)
- 업데이터 플래그 `/setting/updater/mode` (L011), 저장 2계층(Backup.bin BK4) (L024)
- SF 네이티브 클라이언트 경로는 버퍼 큐잉 실패 → Rigel 직접이 정답 (L009, observed)
원장 원본 표는 `packages/data/re/ledger.tsv`.

## 통합 판정 (정적 분석 종료 시점)
**UI 재작성에 필요한 인터페이스는 정적으로 모두 식별됐다.** GPU 드라이버, 윈도 서버, 카메라 엔진을 직접 구현할 필요 없이 im.elf/Android 라이브러리의 기존 API 호출만으로 구성된다. 남은 것은 실기에서만 확정되는 런타임 미지수이며 [0002](0002.%20trackb-critical-path.md)에 있다.

## 정정 이력 (반복 방지)
1. 설정 숫자 54/55/194/16은 SDCom param ID가 아니라 **메뉴 노드 ID**.
2. 이미지 DB 복원은 SDCom으로 트리거 불가(in-process 전용).
3. 정지영상 재생 SDCom 명령 없음.
4. 휴지통 530 추정은 아티팩트.
5. WBI "업데이트 시 drop 후 새로 생성" 가설 오류.
6. SyncAndroid는 디스플레이/입력 핸드오프가 아님.
7. 다이얼 방향은 local_key_code가 아니라 degree 부호.
