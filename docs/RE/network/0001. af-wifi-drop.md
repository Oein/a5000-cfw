# 0001. AF/라이브뷰 중 Wi-Fi(telnet/adb) 끊김 — 의도인가 부작용인가

> 상태: **derived + emulator-observed**(정적 RE 끝까지 + 순정 커널/모듈을 그대로 돌린 에뮬에서 스케줄링 구성 실측).
> AF 부하의 실제 크기와 최종 판별은 **실기 계측 1회**(§7)로 봉인. 실기 없음(2026-11-20).
> 신뢰도 표기: `observed`(실기) · `emu`(에뮬 실측, 순정 바이너리) · `derived`(정적) · `inferred`(추정).
> 원시 자료(디컴파일, 상태표 덤프, 에뮬 스레드 덤프): `packages/data/re/network/`(gitignored).

## 0. 결론 (TL;DR)

| 질문 | 답 |
|---|---|
| 의도된 Sony 동작인가? | **아니다(부작용).** Wi-Fi를 내리는 경로를 전부 열거했으나(§2) 라이브뷰/AF/센서/렌즈 상태에 묶인 정지·서스펜드·전원 차단 경로는 **하나도 없다.** |
| 그럼 원인은? | **CPU 스케줄링 기아(starvation).** PREEMPT_RT 커널에서 Wi-Fi 데이터 경로 전체가 우선순위 사다리의 **맨 아래**(SCHED_FIFO 1 / CFS)에 있고, av-cam(µITRON)의 태스크 111개가 **같은 Linux 스케줄러 위의 SCHED_FIFO 2–154 커널 스레드**로 돈다. 라이브뷰+AF로 RT 부하가 오르면 RX 하프(ksdioirqd), htc_rx/ath6kl 워크큐(CFS), telnetd/adbd(CFS)가 CPU를 못 받는다(§3). |
| 보조 요인 | ① mmc1(Wi-Fi SDIO) IRQ가 **CPU0 고정**(서브마이크로 링크 IRQ 133, SIO 204, hwtimer0, CPU0 바인딩 av-cam 스레드와 동거). ② `vm.min_free_kbytes = 256`(매우 작음) + ath6kl AMSDU RX 버퍼가 **order-1 GFP_ATOMIC** 할당 → 실기 로그의 `kworker/u:N: page alloc fail: order:1, mode:0x20`과 정확히 일치하는 형태(§4). |
| 공유 HW 자원? | 정적·동적으로 **직접 공유 없음**: SDIO 컨트롤러·IRQ 라인·GPIO 전원핀·클럭게이트 레지스터 모두 렌즈/센서/AF 경로와 별개(§5). 공유되는 것은 **CPU0와 스케줄러, 그리고 원자 메모리 예약**뿐. |
| 고칠 수 있나? | **RAM-only로 완화 가능, 벽돌 위험 0**(재부팅=원복): ksdioirqd RT 승격, mmc1 IRQ affinity를 CPU0→CPU3, `min_free_kbytes` 상향(§6). 영구 변경(insmod 인자·sysctl 파일·커널)은 플래시 쓰기라 **비권장/금지**. |
| 실기 필요 항목 | AF 중 RT 부하 크기, 어느 층(av-cam vs im.elf RR)이 굶기는지, 링크 유지 여부, page-alloc 실패 동시성(§7의 1회 계측). |

## 1. Wi-Fi 데이터 경로와 각 단계의 스케줄링 등급

순정 스택(`emulator/docs/RE_WIFI.md` §2): `libWlanResource`가 `cfg80211 → mmc_core → mmcioWrapper → ath6kl_sdio ath6kl_p2p=1`을 insmod. 
아래 우선순위는 **에뮬(순정 커널 `3.0.27_nl-rt106 SMP PREEMPT RT`, 순정 모듈)에서 Wi-Fi(WPS 푸시)를 켠 뒤 `/proc/<pid>/stat`·`/proc/irq/*/smp_affinity`로 실측**한 값이다(`emu`). 우선순위 구성은 커널/모듈 코드가 정하므로 실기와 동일하다고 본다(`derived` 근거 병기).

| 단계 | 실행 컨텍스트 | 정책/우선순위 | CPU | 근거 |
|---|---|---|---|---|
| ① 카드 IRQ (GIC 221, SDHCI NORINTSTS bit8) | `irq/221-mmc1` (강제 스레드화 IRQ) | FIFO **129** | **CPU0 고정** (smp_affinity=1, /proc/interrupts 전량 CPU0) | `emu`; `__udif_request_irq`@0x401F9538 → `request_threaded_irq`(RT 강제 스레드화). `mmc_hw_irq_handler`@mmc_drv 0x7D08 |
| ② 래퍼가 SDIO IRQ 스레드 깨움 | `mmcio_wrapper_irq_handler`@mmcioWrapper 0x15C | (①안에서) | | `derived` |
| ③ HIF/HTC 메일박스 처리 | `ksdioirqd/mmc0` → `ath6kl_sdio_irq_handler`@0x16CAC → `ath6kl_hif_intr_bh_handler`@0x548 | **FIFO 1** | 0–3 | `emu`; mmc_core `sdio_irq_thread`@0x9340이 `sched_setscheduler(FIFO,1)` |
| ③' 메일박스 읽기는 동기 SDIO 명령 | mmc_drv `mmc_hw_exec_command`@0x84B8가 ①의 eventflag 대기 | 명령 150 ms(+850 ms 재시도) / 데이터 10 s 타임아웃 | | `derived` |
| ④ 수신 패킷 후처리 | `htc_rx` 워크큐(WQ_UNBOUND\|WQ_MEM_RECLAIM, `ath6kl_htc_create`@0x3D9C) → `kworker/u:N` | **CFS** | 0–3 | `derived` + `emu`(kworker/u 정책 0) |
| ⑤ 송신 비동기 쓰기 | `ath6kl` 워크큐(`ath6kl_core_init`@0xBAA4, 같은 플래그) | **CFS** | 0–3 | `emu`(`ath6kl` 레스큐어 스레드 정책 0) |
| ⑥ 사용자 공간 | telnetd, adbd, wpa_supplicant, WS_SubProcess | **CFS** | 0–3 | `emu` |

즉 **카드 IRQ 상단(①)만 FIFO 129**이고, 실제 패킷을 꺼내고(③) 처리하고(④) 보내는(⑤) 일은 전부 FIFO 1 또는 CFS다.

## 2. "의도적 정지" 경로 전수 조사 — 이미징 트리거 없음

### 2.1 libNetService (WCM) 상태기계
`stateEvtTbl_*` 테이블(.data, 12바이트 `{event, handler, next_state}` 엔트리, 핸들러는 동적 재배치로 채워짐)을 재배치까지 풀어 전수 덤프했다. 이벤트 번호는 상위 바이트가 출처(0x0xx=API, 0x4xx=IM, 0x5xx=WS, 0x7xx=WR, 0x8xx=RM …).

| 상태(테이블 VA) | Wi-Fi를 내리는 이벤트 → 핸들러 |
|---|---|
| `DRIVER_LOADED` (0xBE29C) — Android `wifi_load_driver` 경로가 머무는 상태 | ev13 API UNLOAD_DRIVERS → `funcUnloadDriversWrStopWlan`(0x4DCA0); **ev1025(0x401) → `funcLoadDriversLoadedSuspend`(0x5105C)** |
| `LOAD_DRIVER_PROC2` / `UNLOAD_DRIVER_PROC1` | ev1025 → `funcLoadDriversProcSuspend`(0x510F4) / `…UnloadSuspend`(0x51094) |
| `*_FUNC_STARTED` 계열 | ev11 API STOP_FUNC → `funcStopWsStop` |
| `HARDWARE_ERROR_DETECTED*` | `funcHwErrStopWlan`(0x4DF3C) / `funcHwErrHandle` |
| `SHOE_DETACH_*` | 핫슈 Wi-Fi 액세서리 분리 → `funcShoeDetachStopWlan` |

- **0x401 = `EN_EVT_IM_API_SUSPEND`**: 유일한 송신자는 `netservice_sus`(0x4C184)이며, 이것은 IMDB 모듈표(`libIMDB`, 모듈 0x13E: `init=netservice_init sus=netservice_sus res=netservice_res`)의 **시스템 서스펜드 콜백**이다(전원 OFF/대기 진입 시 im.elf 모듈 매니저가 호출). 같은 패턴: `wlanResource_sus`(libWlanResource 0x2D24), Android `SyncAndroidService.Suspend(im_type)`. → **라이브뷰/AF와 무관.**
- 리소스 매니저 이벤트는 **획득(0x801 RM_RESOURCE_ACQUIRED)만** 있고 "선점/회수" 이벤트가 없다 → 이미징이 Wi-Fi 리소스를 빼앗는 경로 자체가 없다.

### 2.2 카메라 쪽(libObj/im.elf)
- libObj 문자열/임포트에 Wi-Fi 전원절약·TX 금지·정지 호출 없음(`power_save`, WMI power mode, `stopWlan` 등 0건). Wi-Fi 관련은 메뉴/앱 이벤트(`MSGID_WIFI_*`), 팩토리 테스트(`WLAN_*`), `wlanWatcher_checkAndRebootSet`(libNetCommon 0xA108: Wi-Fi **정지 시퀀스가 폭주할 때** 프로세스 abort 하는 감시자 — 이미징 무관)뿐.
- `iw ath0/ath1 set power_save off`는 시작 시 한 번(`WlanResourceSetMaxPerformanceMode`), 이후 바꾸는 코드 없음.

### 2.3 오류 유발형 정지(부작용이 의도적 정지로 번지는 경로)
- mmcioWrapper `sub_24`(0x24)가 `mmcio_complete_irq/start_irq` 실패 시 **0xE0000001**, LED-valid 실패 시 0xE0000002를 WlanResource 큐 0xA504FA로 보냄 → `processMessage`(0x5F50)가 이벤트 0xE001(HW 에러) + `noticeWifiInh`(0x2BF8, InhMgr factor 0x69F) → NetService `HARDWARE_ERROR_DETECTED` → **Wi-Fi 정지 + 금지(재시작 전까지)**.
- 이 경로는 **자동 복귀하지 않는다.** 관찰된 증상(라이브뷰를 벗어나면 저절로 복귀)과 맞지 않으므로 주원인이 아니다. 다만 기아가 길어 mmc_drv 타임아웃까지 가면 최악의 경우 이 경로로 영구 다운될 수 있다(§7 판별 항목).

### 2.4 Android 쪽
- OpenMemories-Tweak의 `DisableWiFiOnSuspend` 리시버는 `SyncAndroidService.SUSPEND`(=시스템 서스펜드)에서만 `setWifiEnabled(false)` → AF 무관.
- Android 2.3 `WifiService`의 화면꺼짐 유휴 정지(DEVICE_IDLE, 기본 수 분 단위 타이머)는 존재하나 AF 즉시성과 맞지 않음. `services.dex`가 odex 최적화 명령이라 jadx로 본문 미해석 `[?]`(소니 수정 여부 미확인 — 단, 즉시 끊김을 설명하지 못함).

### 2.5 "의도"와 "칩 리셋/브라운아웃"을 배제하는 관찰 근거
- 의도적 정지라면 드라이버 언로드 → 재로드·재결합·DHCP가 필요하고 Android 쪽에서 다시 켜야 한다. HW 에러 경로는 금지 플래그까지 건다. 실기에서는 **라이브뷰를 벗어나면 저절로 복귀**(`observed`, misc 0005).
- 칩 브라운아웃/펌웨어 크래시라면 ath6kl 복구가 필요한데 **`recovery_enable=0`**(.bss 0x1D474, 에뮬 `/sys/module/ath6kl_sdio/parameters` 실측)이라 자동 복구가 없다. `heart_beat_poll=2000`(.data 0x1CA20)은 recovery가 꺼져 있어 타이머조차 등록되지 않는다(`ath6kl_core_init` 끝, `ath6kl_recovery_init`@0x180EC). → 자동 복귀와 모순.
- 반면 **기아**는 자원이 풀리면 흔적 없이 재개된다: 칩 펌웨어(FullMAC)가 비콘·ACK·결합 유지를 자체 처리하므로 호스트가 잠시 메일박스를 못 비워도 결합은 남고 패킷만 칩 버퍼에서 버려진다 `inferred`.

## 3. 근본 원인 체인 — PREEMPT_RT 우선순위 사다리

### 3.1 av-cam은 "별도 세계"가 아니라 같은 Linux 스케줄러 위의 RT 커널 스레드
- `liro.ko` `os_create_task`(0xD98)가 µITRON 태스크마다 커널 스레드 `liro-kliro_<id>`를 만들고, `os_tsk_setprio`(0xCE8)가 **`sched_setscheduler(SCHED_FIFO, 159 − itron_pri)`**(ARM EABI syscall 156)를 호출. CPU 고정은 `os_thread_bind`(0xE68, cfg의 cpu 필드).
- 커널 `__sched_setscheduler`(0x4005A5FC)가 `prio ≤ 159`를 허용(소니 커널 MAX_USER_RT_PRIO=160).
- av-cam ISR은 `os_request_irq`(0xF60) → 커널 `subsys_request_irq`(0x40051BD8, 플래그 0x10020 = IRQF_NO_THREAD\|IRQF_DISABLED)가 **흐름 핸들러를 직접 설치 + IRQ별 affinity 지정** → 스레드화되지 않은 하드 IRQ.

### 3.2 실측 우선순위 지도 (`emu`, 순정 부팅, 라이브뷰 화면)

| 계층 | 스레드 | SCHED / prio | 비고 |
|---|---|---|---|
| 커널 관리 | migration/N, watchdog/N, posixcputmr/N | FIFO 159 | |
| **av-cam (µITRON)** | `liro-kliro_*` **111개** | **FIFO 1–154** (45개가 >129, 110개가 >1) | cfg pri 5→154, 88→71 … 수식 일치 |
| Linux 장치 IRQ 스레드 | `irq/N-*` (mmc1 포함) | FIFO 129 | |
| softirq | ksoftirqd/N | FIFO 128 | |
| im.elf | 158 스레드 중 **68개 SCHED_RR** (1–123; `Appframework`=RR 1, 34개 RR 8, 16개 RR 6 …) | RR | 라이브뷰 OSD/엔진 제어 |
| Sony 커널 서비스 | memmgr 123, UTIMER* 7, UPM_DFS 6 … | FIFO | |
| **Wi-Fi RX 하프** | **ksdioirqd/mmc0** | **FIFO 1** | Appframework(RR1)·kliro_120(FIFO1)과 동급 |
| **Wi-Fi RX 후처리/TX** | kworker/u:N (htc_rx, ath6kl wq) | **CFS** | |
| **원격 접속** | telnetd, adbd, wpa_supplicant | **CFS** | |

- RT 스로틀링 sysctl(`/proc/sys/kernel/sched_rt_runtime_us`)이 **존재하지 않는다**(`emu`) → RT가 CPU를 다 쓰면 CFS가 보장받는 몫이 확인되지 않음 `[?: 커널 내부 기본값 존재 여부]`.

### 3.3 IRQ 배치 (`emu`, `/proc/irq/*/smp_affinity` + `/proc/interrupts`)

| CPU | 주요 IRQ |
|---|---|
| CPU0 | **221 mmc1(Wi-Fi)**, 133 서브마이크로 스트로브(p0.12, 에뮬에서 최다 발생), 204 SIO ch3, 158 hwtimer0, 152 UART, 76 GPU, 189/192 DMAC |
| CPU1 | 98 SYSV 프레임, 101/102 디스플레이 vsync, 202 SIO ch1, 216 ADC |
| CPU2 | **35/36/67/83/84 CamCore/ISP**, **173/174 렌즈 UART1 mdma(TX/RX)**, 151 PL011, 163/164 타이머 |
| CPU3 | (av-cam 바인딩 최소) |

AF 경로(렌즈 직렬 + 콘트라스트 AF 평가)는 CPU2에 몰리고, CPU 미고정 av-cam 태스크(59개, 그중 19개 FIFO>129, 58개 FIFO>60)는 RT push/pull로 다른 코어로 넘친다. Wi-Fi는 하드 IRQ 상단이 CPU0에 묶여 있고 나머지는 FIFO 1/CFS라, **4코어 모두에서 FIFO≥2 작업이 이어지면 ③④⑤⑥ 전부가 멈춘다**. ICMP 응답도 netif_rx 이후 softirq(③의 문맥)에서 나오므로 ping 100% 손실과 포트 무응답이 동시에 나타나는 관찰(`observed`)과 정합.

### 3.4 에뮬 부하 비교(정성)
`/proc/<pid>/stat` utime+stime 20 s 창(TCG라 절대값 무의미, 렌즈 없음 → AF 미구동):
- 라이브뷰: av-cam RT 888 tick, im.elf(대부분 RR 스레드) 1037 tick.
- 반누름(S1, 렌즈 없음=AE만): 거의 동일.
- MENU: av-cam RT 788 tick 유지, im.elf ≈ 0.
→ 라이브뷰는 im.elf RR 층 부하를 크게 올리고, av-cam RT 층은 상시 존재. 실기의 AF는 여기에 CPU2 렌즈/ISP 루프를 더한다 `inferred`. **실제 AF 증분은 에뮬로 재현 불가**(렌즈 HLE가 AF 루프 미구동, TCG 타이밍) → §7.

## 4. 메모리 보조 요인
- `vm.min_free_kbytes = 256`(`emu`, 순정 값) — 175.8 MB 시스템치고 매우 작음. 에뮬 Wi-Fi 동작 중 MemFree ≈ 0.5 MB(대부분 page cache).
- ath6kl AMSDU RX 버퍼: `ath6kl_refill_amsdu_rxbufs`(0x100C4) → `ath6kl_buf_alloc(3996)`(0xA774) → `dev_alloc_skb(4187)` → SLAB size-8192 = **order-1, GFP_ATOMIC(0x20)**. 일반 RX 버퍼(`ath6kl_rx_refill`@0xFFE8, 1664 B)는 order-0.
- 실기 dmesg 캡처에 Wi-Fi 동작 중 **`kworker/u:2: page alloc fail: order:1, mode:0x20`**(t≈142 s)가 있다(`observed`, 당시 라이브뷰 여부 미상). 형태(언바운드 kworker, order-1, 원자)가 htc_rx/ath6kl 언바운드 워크큐의 AMSDU 버퍼 보충과 정확히 일치 `inferred`.
- 할당 실패 시 ath6kl은 보충을 건너뛰고(`ath6kl_rx_refill` break), HTC는 RX 버퍼가 없으면 수신을 막는다("host has no rx buffers blocking receiver") → 메모리가 풀릴 때까지 RX 정체. 라이브뷰가 페이지 캐시/버퍼를 더 쓰면 악화(메모리 상세는 [memory 0001](../memory/0001.%20ram-footprint-and-trim.md)).

## 5. 공유 HW 자원 점검 (Q2) — 직접 공유 없음

| 자원 | Wi-Fi | 렌즈/센서/AF | 공유? |
|---|---|---|---|
| 호스트 컨트롤러 | mmc1 F_SDH30 0xF0301000 | (av-cam MMIO 목록에 0xF030xxxx 없음) | 아니오 (`derived`, av-cam.mmio) |
| IRQ | GIC 221 → CPU0 | 173/174(mdma), 35–38/67–84(ISP) → CPU2 | 라인 공유 없음, **CPU0는 133/204와 공유** |
| 전원/리셋 핀 | GPIO p6.2, p6.3(공급), p1.4(PWD_L), p3.0–5(SDIO 핀) | 렌즈 P0.5/0.9/2.10/2.11/5.4, av-cam 직접 GPIO는 p0(0xF2910000)만 | 아니오 |
| 패드/핀먹스 블록 0xF2912000 | +0x344/0x348/0x354/0x548/0x554 | av-cam +0x000–0x058 | 같은 블록, **다른 레지스터** |
| 클럭 게이트 | 0xF2A30070(clkrst4, mmc slot1) | av-cam 0xF2A31xxx/0xF2A32xxx | 아니오 |
| DMA | mmcioWrapper 32 KiB 바운스 + SDHCI | av-cam 16ch mdma(0xF0102000) | 아니오 |
| 드라이버 락 | mmc_drv 슬롯별 hw 세마포어 | SD(mmc0)와 같은 mmc_drv, 전역 락은 IRQ 등록 시뿐 | 사실상 아니오 |
| DFS(UPM) | mmc_drv는 자체 base clock(`mmc_hw_set_basefreq`), DFS 콜백 미등록 | UPM_DFS FULL/HALF 전환 | 간접 영향 `[?]` |

## 6. 수정/회피 옵션 (벽돌 위험·실현성 순)

모두 **RAM-only, 재부팅으로 원복**(CLAUDE.md §1의 "자유롭게" 등급). 최악의 실패 = 엔진 지연/oops → 물리 전원 재부팅(벽돌 아님). 먼저 에뮬에서 적용 가능성 확인, 실기는 §7 계측과 함께.

| 순위 | 옵션 | 방법 | 효과 기대 | 위험 |
|---|---|---|---|---|
| 1 | **운영 회피(현행)** | LV/AF 중엔 원격 의존 X, 로그는 tmpfs 링버퍼 → 메뉴 복귀 후 수집 | 확실 | 없음 |
| 2 | **mmc1 IRQ를 CPU0→CPU3** | `echo 8 > /proc/irq/221/smp_affinity` (에뮬에서 쓰기 수락 확인, 실제 이동은 트래픽 시 검증 필요 `[?]`) | IRQ 상단 지연↓ (CPU0 동거 IRQ 회피) | 낮음 |
| 3 | **ksdioirqd/mmc0 RT 승격** | busybox에 `chrt` 없음 → 정적 소형 헬퍼(sched_setscheduler)로 FIFO 50–60 대역(=im.elf RR 대부분(≤9)보다 위, av-cam(≥69)·IRQ(129)보다 아래인 **빈 대역**) | im.elf RR 층 기아는 해소. av-cam 층이 원인이면 부분 효과 | 낮음. av-cam 위로 올리는 건 계측 후에만(엔진 데드라인 위험) |
| 4 | **원격 접속 프로세스 RT 소폭 승격** | telnetd/adbd(+그 자식 sh)를 같은 헬퍼로 FIFO 2–5 | CFS 전멸 시에도 셸 응답 | 낮음(대량 출력 시 im.elf RR1 Appframework와 경쟁) |
| 5 | **`vm.min_free_kbytes` 상향** | 256 → 1024–2048 (`/proc/sys/vm/min_free_kbytes`, 휘발) | order-1 원자 할당 실패↓ | 낮음(가용 메모리 수 MB 감소 → APK 설치 등 OOM 여유 축소, memory 0001 참조) |
| 6 | 워크큐 처리 승격 | htc_rx/ath6kl은 공용 kworker/u 풀(CFS)이라 개별 승격 불가. kworker/u 일괄 승격은 부작용 큼 | 제한적 | 중간 → 비권장 |
| — | ath6kl `recovery_enable`/`heart_beat_poll` | `/sys/module/.../parameters`(0644)로 쓰기는 되나 **코어 init 때만 읽음**, Wi-Fi off 시 rmmod로 값 소실 → insmod 인자 변경(플래시) 필요. 또 기아에는 무효 | 없음 | 플래시 → **금지** |
| — | im.elf 안 "Sony Wi-Fi 서스펜드 호출" 후킹 | **그런 호출이 존재하지 않음**(§2) | 해당 없음 | — |
| — | CT_ID_SET_NETWORK_ENABLE / 재연결 가속 | 결합이 유지된다면 불필요(§7에서 확인). 끊긴다면 wpa_supplicant 재결합은 자동, DHCP(pump) 재요청만 문제 | 조건부 | 낮음 |
| — | USB를 제어 채널로 | 순정 USB 가젯은 `usbg_storage`(MSC)·`usbg_stillimage`(PTP)·`usbg_sen`·`usbg_buspower`·`usbg_cmn`뿐 — **네트워크/시리얼 가젯 없음**. 대안: (a) PTP 벤더 오퍼레이션 메일박스(추가 RE 필요), (b) 소니 3.0.27-rt106 + fusb 가젯 스택에 맞춘 자작 가젯 모듈을 tmpfs에서 insmod(벽돌 아님, 커널 oops=재부팅, 공수 큼). MSC는 촬영과 배타 | 근본 회피 | 중간(공수) |
| ✗ | 영구 변경(insmod 인자, sysctl 설정 파일, 커널/initrd) | 플래시 쓰기 | — | **금지(벽돌 등급)** |

권장 조합: **2 + 3(FIFO 50대) + 4 + 5**를 하나의 tmpfs 스크립트로(원복 스크립트 동봉), §7 계측의 A/B로 효과 확인 후 필요 시 3을 상향.

## 7. 실기 1회 계측으로 봉인할 것 (읽기 위주, 상태 변경은 사용자 확인 후)

**로거**: tmpfs(`/android/a5k/`)에 100 ms 주기 셸 루프 — `/proc/uptime`, `/proc/net/dev`의 ath0 rx/tx 패킷, `/proc/interrupts`의 mmc1 CPU별 카운트, `/proc/meminfo` MemFree, ksdioirqd·kworker/u의 `/proc/<pid>/stat`(상태·utime), `dmesg` 신규 줄, `wpa_cli status`(bssid/state, 1 s 주기). 로거 자신은 CFS면 굶으므로 **샘플 간격의 공백 길이 = 기아 시간**(그 자체가 측정값). 헬퍼로 FIFO 50 로거를 하나 더 두면 정확한 타임라인 확보.

**절차**: 메뉴(기준) 30 s → 촬영화면 라이브뷰 30 s → 반누름 AF 10 s ×3 → 메뉴 복귀 → 로그 회수. 호스트는 타임스탬프 ping.

| 관찰 | 판정 |
|---|---|
| mmc1 IRQ 카운트는 증가, ath0 rx·ksdioirqd utime 정체, CFS 로거 공백 | **스케줄링 기아 확정**(본 보고서) |
| mmc1 IRQ도 정지, wpa_cli는 COMPLETED | 칩/SDIO 측 정체 → 클럭/DFS `[?]` 재조사 |
| ath0 소멸·모듈 언로드·wpa_supplicant 종료·HW 에러 이벤트 | 의도적/에러 정지(본 보고서와 모순 → §2.3 경로 재검토) |
| wpa_cli DISCONNECTED/재결합 | 링크 계층 손실(AP 측) → 재연결 가속 옵션 검토 |
| AF 시점에 `page alloc fail order:1` 집중 | 메모리 레그 기여 확정 → 옵션 5 우선 |

그 후 옵션 2/3/4/5를 적용한 상태로 같은 절차를 반복(A/B).
