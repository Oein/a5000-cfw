# 0005. Warm 부팅(WBI 스냅샷 재개) — 복원 시퀀스와 에뮬레이터 구현

> 설정-읽기 assert에서 중단 — 정확한 벽 §5). 2026-11-21. 부트로더/스냅샷 바이트는 전부 device-private(미커밋).

## 0. 요약

| 질문 | 답 |
|---|---|
| 카메라의 "warm 재개"는 몇 종류인가 | **두 가지.** (1) **HOT**(boot mode 2): warm off에서 micro가 DDR을 self-refresh로 유지 → 부트로더가 resume 벡터로 점프(DDR 재적재 없음). (2) **SS**(boot mode 11): DDR 손실 시 부트로더가 공장 WBI 스냅샷(nflasha5)을 DDR로 적재 후 재개. 둘 다 "제자리 재개"이고 `/sbin/init`은 **재실행되지 않는다**. |
| 본 보고서 대상 | **SS(WBI 스냅샷 재개)**. HOT은 에뮬에 이미 구현됨(RE_WARM_RESUME §3·§7). |
| SS 진입점 | nflasha5 헤더 `WBI1`, 0x431=1073 섹션, flag 9(압축), 헤더 resume 벡터 **0x800523BC** = `cxd90014_cpu_resume_ssboot`. |
| SS 진입점이 하는 일 | `cxd90014_cpu_resume_ssboot`(0x400523BC)은 **r1=4를 `cxd90014_ssboot_stat`(0x400523A0)에 기록**한 뒤 곧바로 `cxd90014_cpu_resume`(0x400523CC)로 **낙하(fall-through)**. 즉 SS 재개 코드는 HOT 재개 코드와 **ssboot_stat=4 설정 한 가지만** 다르고 CPU 컨텍스트 복원은 전적으로 동일. |
| 압축 해제(lz77)는 재구현해야 하나 | **아니오.** 공장 스냅샷은 `tools/wbi.py`로 이미 해제되어 `ram.bin`(121.5MB) + `map.tsv`(1073행 `offset pa va len`)로 추출돼 있음. SS 재개는 각 섹션을 PA로 복사하는 섹션-카피이며, 부트로더의 lz77 디코더/부트로더 디스어셈블은 **불필요**. |
| 부트로더를 NAND.BIN에서 디스어셈블했나 | **필요 없었다**(§4 체크포인트). 복원에 필요한 모든 요소(헤더 포맷·resume 벡터·압축 해제 결과·CPU 복원 코드·결정 규칙)가 (a) nflasha5 헤더, (b) 해제된 스냅샷, (c) 커널 `vmlinux.elf`에 전부 존재. 부트로더/커널 warm 확장 자체는 여전히 펌웨어 밖이지만, 에뮬레이션에 그 코드는 요구되지 않음. |

## 1. SS 재개 시퀀스 (복원 단계)

### 1.1 헤더와 결정
- nflasha5 헤더(`fwtool WbiHeader`): 매직 `WBI1`, 섹션 수 0x431(1073), flag 9(압축), **resume 벡터 0x800523BC**, 버전 0x20060224.
- warm/cold 및 HOT/SS 결정은 부트로더가 micro의 warm 플래그(slot-A TX +0x1B bit0) + `pm.sus_error`(hand-off +0x60) + WBI 유효성으로 수행(RE_WARM_RESUME §1.3·§2.1). cmdline의 `warm.mode`/`ignore_drop`은 커널 쪽 파라미터. 부트로더 코드는 펌웨어에 없어 규칙은 derived.
- SS는 **DDR 손실 + WBI 유효**일 때. DDR 유지면 HOT, WBI drop이면 full cold(boot mode 1).

### 1.2 스냅샷 적재(압축 해제 결과) → DDR
- 섹션 맵(`map.tsv`): 1073행, 각 행 `offset_in_ram.bin  physical_addr  kernel_VA  length`.
- PA 커버리지 **0x80021000 .. 0x9EC30000**, 총 121.5MB(희소; Linux 커널/앱 RAM + 엔진 예약 영역 0x82·0x8C·0x8D·0x8F·0x91·0x9EC... = cmdline `wbimem=` 영역과 일치).
- **스냅샷에 없는 구간**: 0x80000000..0x80021000(memrsv 0x28000@0x80000000의 앞부분 = MUMIN FTL 하드오프). 공장 스냅샷이 의도적으로 제외 → 부트로더가 매 부팅 재구성(§5·§3 함정).

### 1.3 CPU/MMU 상태 복원 (`cxd90014_cpu_resume`, 0x400523CC, PA 진입)
HOT와 공유. 스냅샷에서 읽은 실측값(`tools/wbi.py`):
- `cxd90014_ssboot_stat`(0x400523A0): 스냅샷 RAM엔 2, 진입 코드가 **4로 덮어씀**.
- `pm_mem_alive`(0x403946BC) = **0**(스냅샷 재개 표식) → 재개 후 `cxd90014_pm_enter`가 `WARMBOOT` 출력 + `ssboot_setmode`.
- PM state(0x4037947C) = **4**(warm).
- `sleep_save_sp`(0x4005249C) = **0x8AB9BE28**(DDR 내 저장 컨텍스트 블록 PA). 복원 레지스터: DACR 0x15, CPACR 0xC0F00000, TTBCR 0, TTBR0 0x8AB8804A, TTBR1 0x8003404A, CONTEXTIDR 0xED, **SCTLR 0x10C5387D**(M=1), ACTLR 0x6041.
- 복원 순서(코드): CPSR#0xD3 → 캐시 flush → MMU/캐시 off → `pl310_init` → `cxd90014_smp_init`(메일박스 0xC0005010/14/18) → `sleep_save_sp`에서 DACR/CPACR/TTBCR/TTBR0/TTBR1/CONTEXTIDR/TPIDR/PRRR/NMRR/SCTLR/ACTLR/sp 복원 → SCU → **`resume_turn_on_mmu`**(0x80052480: `mcr SCTLR`로 M=1, nop, `mov pc,r1`) → `resume_after_mmu`(0x400524A0: `pop {r4-pc}`로 `cxd90014_pm_enter`로 복귀).

### 1.4 resume PC와 MMU-enable 함정(HOT와 동일)
- MMU-on 직후 2명령(0x80052484, 0x80052488)을 **DDR XN identity 매핑**에서 페치 → QEMU는 SCTLR 쓰기를 즉시 반영해 prefetch permission fault. 실제 Cortex-A5는 SCTLR 쓰기 전 페치된 명령을 실행. 해결 = CPU 속성 **`sctlr-fetch-delay`**(RE_WARM_RESUME §3.3). SS는 이 경로를 그대로 재사용.

## 2. 에뮬레이터 구현 (SS 머신 모드)

파일: `packages/emulator/qemu-overlay/hw/arm/sony_a5000.c` (overlay; upstream 수정 없음).

- 머신 옵션 **`-M sony-a5000,wbi-snapshot=<DIR>`**: `<DIR>`에 `ram.bin`+`map.tsv`(device-private, 런타임 적재). `run.sh`는 **`A5K_WBI_SNAPSHOT=<DIR>`** 환경변수로 노출.
- 동작: cold power-on(초기/전원 사이클/SoC 리셋, HOT 아님)에서 full cold 대신 **SS 스냅샷 복원** 수행.
  1. DDR·IRAM clear(전원 손실),
  2. `a5k_ssboot_load()`: `map.tsv` 각 행을 `ram.bin[offset..]`에서 PA로 `address_space_write`(DDR 범위만),
  3. **NAND/MUMIN 하드오프 자동 로드(기본)**: `<wbi-snapshot>/nand_lowmem.bin`을 0x80000000에 기록(블로커1, device-private 런타임 파일; 없으면 경고 후 진행; env `A5K_SS_LOWMEM`로 경로 override),
  4. 부트 스텁 entry literal = **0x800523BC**, CPU0 sp = 0xC0020000(HOT와 동일 근거),
  5. 스텁이 GIC 프로그래밍 후 resume 벡터로 진입.
- HOT(`warm-resume=on`)와 공존: warm off→HOT(DDR 유지), cold/초기→SS(스냅샷). 옵션 미지정 시 **기존 full cold 부팅 그대로**(무회귀, cold 부팅으로 촬영 UI 도달 재확인).
- 스냅샷/부트로더 **바이트는 소스에 포함하지 않음** — 전부 런타임 파일 적재.

## 3. 검증 결과

| 단계 | 결과 |
|---|---|
| 스냅샷 적재 | 1073 섹션, 127,430,656 B, 0 skip → DDR. |
| SS 진입 | `power-on, SS WBI-snapshot boot -> 0x800523bc`, cold stage-1 없음. |
| 커널 재개 | `WARMBOOT`(스냅샷 재개 분기), CPU1~3 up, `PM: early resume of devices complete`. **MMU on**(PC가 커널 VA에서 실행, `sctlr-fetch-delay`로 fault 없음). |
| 디바이스 재개 | **MUMIN 하드오프 기본 자동 로드 후**(§2.1) mumindrv 정상 재개, b-252·utm·uipc·utimer·backup까지 **UDIF 체인 완주**, `PM: resume of devices complete`, `Restarting tasks ... done.` (재개 전체 ~88ms). 하드오프 없으면 mumindrv 재개 실패→UDIF 중단→검정(블로커1). |
| 시간 연속성 | printk 타임스탬프는 리셋 타이머를 따라 0부터 재시작(HOT와 동일 현상). cold 대비 stage-1·`Linux version` 배너 없음 = 제자리 재개. im.elf가 assert로 죽어 `/proc/uptime`은 셸로 못 읽음(스냅샷 공장 `ttynull` 콘솔). |
| userland | 디바이스 재개 후 **im.elf 해동**되어 실행(pid 148). 그러나 UI 완성 직전 **assert→abort**: `dmpNative::SystemImpl::initialize_setting()`가 `Backup_nread(bkid=0x01700000, dst, 4)`(libObj.so+0x5DAFDA) 호출 후 반환≠4 → `assert(bret==sizeof(this->setting))`(SystemImpl.cpp:156) → `abort`/`raise(SIGABRT)`(libc) → im.elf 종료 → 검정. |

**블로커1 — MUMIN 하드오프(정식 수정 완료, §2.1)**: 스냅샷은 0x80000000..0x80021000(MUMIN FTL 하드오프)을 제외. cold 부팅은 stage-1 `nand.ko boot_mode=1`이 이 영역을 NAND에서 재구성하지만 SS는 stage-1을 건너뜀 → `mumin_register_devctrl_info ... stat 0` 실패 → UDIF 중단. 이 영역은 NAND-콘텐츠 의존(블록 변환 테이블, 헤더 매직 `iMuM`)이라 C 구조 재생성 = MUMIN FTL 재구현이므로 비현실적. 대신 `ram.bin`/`map.tsv`와 동일하게 **스냅샷 디렉토리의 device-private 런타임 아티팩트(`nand_lowmem.bin`)로 기본 자동 로드**(바이트 미커밋; cold 부팅에서 `pmemsave 0x80000000 0x21000`으로 1회 캡처). = 보드가 부트로더 대리로 SS 경로의 NAND 하드오프 제공. 주입 후 mumindrv 정상 재개 + UDIF 완주 **확정**.

## 4. Phase-1 체크포인트 판정

- **복원 시퀀스는 에뮬레이션에 충분히 확정**됨(헤더·결정·압축해제결과·상태복원·resume PC 모두 확보). 부트로더/커널 warm 확장 코드는 펌웨어 밖이지만 **요구되지 않음** — SS 진입은 HOT 재개 코드 + ssboot_stat=4, 스냅샷은 이미 해제됨.
- NAND.BIN 부트로더 디스어셈블은 **불필요**했다. 따라서 "부트로더가 덤프에 없어 불가" 상황이 아니라 **구현 가능**으로 판정, 구현함.
- 남은 미해결은 복원 시퀀스가 아니라 **디바이스/userland 정합성**(§5).

## 5. 남은 블로커 (device-only / 엔진 정합성)

1. **MUMIN 하드오프 재현(해결 경로 확정)**: SS 경로에서 보드가 0x80000000 NAND 하드오프를 부트로더 대리로 생성해야 함. 실험으로 cold 캡처 주입이 유효함을 확인; 정식 구현은 stage-1 `nand.ko boot_mode=1` 하드오프 구조(매직 `iMuM`)를 보드가 직접 기록하거나, SS 직전에 최소 NAND 재초기화를 수행.
2. **im.elf 설정-읽기 정합성(핵심 블로커, 정확히 특정됨)**: 디바이스 재개(UDIF 완주) 후 im.elf 해동, UI 완성 직전 **assert 실패→abort**. 체인(gdb 동적 확정): `dmpNative::SystemImpl::initialize_setting()`(libObj.so+0x5DAFCx대) → `Backup_nread(bkid=0x01700000, dst=&this->setting, nbytes=4)`(libObj+0x5DAFDA) → 반환 바이트수 ≠ 4 → `__assert_fail("bret == sizeof(this->setting)", "SystemImpl.cpp", 156, ...)`(libc 0x1FBCC) → `abort`→`raise(SIGABRT)`→ Sony em가 `vector exception (0x000)`로 표시, im.elf 종료.
   - **엔진-상태 read**: Backup prop **0x01700000**(4바이트, dmpNative 설정, 값 0). 이 prop은 **UI 브링업 경로의 필수 Backup 읽기**로 이미 알려짐(`RE_UI_BRINGUP.md` §7 item 8: "0x01700000 (4 B, dmpNative setting, __assert_fail if read size ≠ 4)"). 에뮬은 Backup prop을 보드 훅이 아니라 **게스트 `backup.ko`의 Backup.bin RAM 사본**에서 서빙하며, **cold 부팅에선 이 읽기가 4를 반환**(촬영 UI 도달). SS 재개에서만 ≠4.
   - **왜 SS에서만 short인가(derived)**: SS는 `ssboot_stat=4`+`WARMBOOT`+`ssboot_setmode`로 "스냅샷 부팅"을 userland에 알려 `initialize_setting`류 재-초기화를 유발하는데, 그 시점 Backup 서빙이 4바이트를 주지 못함. 유력 원인은 (a) `backup.ko` 재개 후 Backup.bin 재읽기가 SS NAND/FTL 잔류 비정합(블로커1을 해결해 mumindrv는 재개했으나 공장 스냅샷의 FTL 상태 vs 에뮬 NAND 모델이 읽기 레벨까지 완전 정합은 아님)으로 short, 또는 (b) 해동 순서상 dmpNative 스레드가 backup 서빙 준비 전에 선행. (스택이 frame-pointer 없이 stripped라 호출자 체인 정적 복원 불가 → 정밀 귀속은 device-only.)
   - **최소 스텁 방향**: SS 재개 경로에서 `Backup_nread(0x01700000)`(및 동류 dmpNative 설정 prop들)이 4바이트(값 0)를 반환하도록 보장. 에뮬이 Backup을 게스트 `backup.ko`에서 서빙하므로 보드 단독 스텁이 어려움 → 필요한 것은 (i) `backup.ko` 재개 시 Backup RAM 사본이 온전/서빙 가능함을 보장(SS NAND 읽기 경로 정합 = 블로커1의 FTL 읽기 레벨 확장), 또는 (ii) HLE로 SS 경로에서 Backup 읽기 결과를 강제(AI_WORKFLOW §1.5 문서화). 어느 쪽도 **NAND/FTL 재개 정합 또는 backup.ko 재개 RE**를 요구하는 device-coherence 작업 — 복원 메커니즘 결함이 아님.
   - 진척: 커널·**전체 디바이스 재개**·userland 해동까지 모두 성공, UI는 이 **단일 설정-읽기 assert** 하나에서 막힘(= 사실상 UI 직전까지 도달).
   - **바운드 프로브(assert 우회 후 그 다음 벽 확인 — 일회성 로컬 실험, 코드 미반영)**: SS resume 메모리의 `initialize_setting` 호출부(libObj) `blx Backup_nread; cmp r0,#4`를 `movs r0,#0; str r0,[r1]; cmp r0,r0`로 패치(설정값 0 저장 + assert 통과), PA 0x8BA9DFDA. (펌웨어 오프코드 시그니처를 담아 **커밋하지 않음** — 결과만 기록.) 결과: **im.elf가 더 이상 abort하지 않음**(klog에 예외/assert 블록 없음, `Restarting tasks ... done.`만), 그러나 **촬영 UI는 렌더되지 않음(패널 검정)**. 시스템이 **정지(quiescent)** — CPU0가 `cpu_v7_do_idle+0x8`(wfi, `default_idle`)에 고정 = 모든 im.elf 스레드가 커널 wait에 블록, runnable 스레드 없음.
   - **그 다음 벽(= 이 실험이 드러낸 첫 번째 다음 벽)**: assert가 아니라 **조용한 엔진/디스플레이 정합성 데드락**. 설정 init 이후 im.elf의 렌더 파이프라인(Rigel/VDF OSD present)이 재개 시 공장 스냅샷이 전제하는 엔진 이벤트/핸드셰이크를 기다리며 블록 → 패널에 OSD 미도달. 단일 fault PC/offset이 없음(크래시 아닌 missing-event 데드락). 후보(미추적, 추측 표시): `RE_UI_BRINGUP.md` §7 gate C "VDF가 모든 OSD send에 MSGID_PIN_SEND_COMP로 응답하지 않으면 두 번째 eglSwapBuffers(및 UI 스레드)가 영구 블록", 또는 av-cam "camera ready"/재개 핸드셰이크. = **전체 warm-SS UI는 이 단일 설정-읽기 뒤 바로 도달 가능하지 않고, 외부(실기) 스냅샷을 재개할 때 에뮬 엔진 모델이 재생성 못 하는 재개 이벤트에 의존**. 코디네이터 지침대로 이 첫 다음 벽만 특정하고 추가 추적 중단.

## 6. 자동 실행(LD_PRELOAD) × warm 재개 판정 — [0003]의 미결 항목 해소

**질문**: 상시 warm 카메라에서 `/setting/mode/dmode`+`/setting/env.txt`(LD_PRELOAD) 자동 실행이 실제로 적용되는가?

**판정**: **warm 재개(HOT·SS 모두)에서는 적용되지 않는다.**
- SS 재개는 공장 WBI 스냅샷을 복원한다. 그 스냅샷은 Sony가 빌드 시 만든 것으로 **우리 파일보다 앞서** 있고 LD_PRELOAD가 들어있지 않다. 재개는 `WARMBOOT`→디바이스 재개→`Restarting tasks`(기존 프로세스 **해동**)로 끝나며 `/sbin/init`은 **재실행되지 않는다**(에뮬 observed: SS 재개 시 ttyAM1 셸이 뜨지 않음 = 스냅샷의 공장 cmdline `console=ttynull`이 유지됨 = init의 `set_oreore_env`가 돌지 않음). 따라서 재개된 것은 preload 없는 공장 `im.elf`(pid 148).
- HOT 재개도 동일(init skip, DDR 유지 이미지 해동). 직전 부팅이 preload 포함 cold였다면 그 `.so`는 살아있는 RAM 이미지에 **이미** 매핑돼 있어 이어지지만, 재개 자체가 preload를 **새로** 걸지는 않는다.

**함의**:
- `/setting` LD_PRELOAD([persistence/0001] 경로 a)는 **콜드 부팅에서만** 트리거된다(init 실행 → `check_mode_file`+`set_oreore_env` → bootin→im.elf 상속). 상시 warm 카메라의 **정상 전원 레버 ON(=warm)에서는 걸리지 않는다**.
- warm에서 우리 UI를 걸려면: (a) **콜드 부팅 강제**(`ud_wbi_drop`로 WBI 무효화 또는 cold-off 타입) 후 그 콜드 경로가 preload를 적용 — 단 WBI 정합성/위험은 [0002]·[persistence/0001] 참조, 또는 (b) **이미 실행 중인 im.elf에 재개 시점에 주입**(route-b/ptrace) — init에 의존하지 않으므로 warm 재개에도 무관. 이것이 route-b가 존재하는 이유이며, warm-항상 카메라에서 route-b가 LD_PRELOAD-자동실행보다 견고한 근거.
